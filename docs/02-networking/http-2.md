## 📖 Deep Dive Notes

### 1. সহজ সংজ্ঞা ও Intuitive Mental Model

২০১৫ সালে IETF দ্বারা প্রমিত (RFC 7540) **HTTP/2** হলো গুগলের পরীক্ষামূলক SPDY প্রোটোকল থেকে উদ্ভাবিত ওয়েব প্রোটোকলের একটি যুগান্তকারী রূপান্তর। 

HTTP/1.1-এর প্লেইন-টেক্সট সীমাবদ্ধতা এবং ৬-কানেকশন লিমিট ভেঙে এটি **একটি একক দীর্ঘস্থায়ী TCP কানেকশনের ওপর বাইনারি ফ্রেমিং এবং মাল্টিপ্লেক্সিংয়ের মাধ্যমে একই সাথে শত শত স্বাধীন রিকোয়েস্ট ও রেসপন্স সমান্তরালভাবে প্রবাহিত করতে সক্ষম**।

```
HTTP/1.1 (Text-based, Serial/Blocking):
[ Client ] ─── GET /a.js (Text) ───────> [ Server ]
[ Client ] <── 200 OK (Wait to finish) ─ [ Server ]
[ Client ] ─── GET /b.css ─────────────> [ Server ]

HTTP/2 (Binary Framing, True Multiplexing):
[ Client ] ─── [Stream 1: Frame A] [Stream 2: Frame B] [Stream 1: Frame C] ───> [ Server ]
(সবকিছু বাইনারি ফ্রেমে বিভক্ত হয়ে একক পাইপ দিয়ে সমান্তরালভাবে মিশে যায়!)
```

> 🧠 **Intuitive Mental Model (একক কনভেয়ার বেল্টে পার্সেল মিক্সিং অ্যানালজি):**
> একটি পোস্ট অফিসের মাত্র একটি কনভেয়ার বেল্ট আছে (**Single TCP Connection**)।
> - **HTTP/1.1:** কনভেয়ার বেল্টে একটি বিশাল বড় বাক্স রাখা হলো। সেই বাক্সটি পুরো বেল্ট পার হয়ে ওপারে না পৌঁছানো পর্যন্ত বেল্টে অন্য কোনো ছোট চিঠি বা পার্সেল রাখা যাবে না (**Serial Blocking**)।
> - **HTTP/2:** প্রতিটি মালামালকে ছোট ছোট টুকরো (Frames) করে প্যাকেটে ভরা হলো এবং প্রতিটি প্যাকেটে কালার কোড বা আইডি নম্বর লাগানো হলো (**Stream ID**)। এবার একই বেল্টের ওপর ১ নম্বর বাক্সের ২টি টুকরো, ২ নম্বর চিঠির ১টি টুকরো এবং ৩ নম্বর বাক্সের ৩টি টুকরো একসাথে পাশাপাশি বেল্টে চালিয়ে দেওয়া হলো (**Interleaving/Multiplexing**)। ওপারে রিসিভার আইডি দেখে টুকরোগুলো মিলিয়ে যার যার আসল পার্সেল বানিয়ে নিল!

### 2. Core Architecture: The Binary Framing Layer

HTTP/2 কোনো এইচটিটিপি সেমান্টিকস (Verbs, Status codes, URI) পরিবর্তন করেনি। পরিবর্তনটি ঘটেছে অ্যাপ্লিকেশন কোড এবং ট্রান্সপোর্ট সকেটের মাঝখানের এনকোডিং লেয়ারে:

```
┌──────────────────────────────────────────────┐
│           HTTP Application Layer             │
│      (GET, POST, Headers, Status Codes)      │
├──────────────────────────────────────────────┤
│          Binary Framing Layer (HTTP/2)       │
│  - Frames: HEADERS, DATA, PRIORITY, RST...   │
│  - Streams: Bi-directional stream of frames │
├──────────────────────────────────────────────┤
│              TLS 1.2 / TLS 1.3               │
├──────────────────────────────────────────────┤
│              TCP Transport Layer             │
└──────────────────────────────────────────────┘
```

#### প্রধান ফ্রেম প্রকারভেদ:
- **HEADERS Frame:** মেটাডাটা এবং কমপ্রেসড HTTP হেডার ধারণ করে (একটি নতুন স্ট্রিম ওপেন করে)।
- **DATA Frame:** রিকোয়েস্ট বা রেসপন্সের আসল পে-লোড বডি ধারণ করে।
- **RST_STREAM Frame:** একটি নির্দিষ্ট স্ট্রিম অবিলম্বে ক্যানসেল করে (বাকি কানেকশন অক্ষুণ্ণ রেখে)।
- **SETTINGS Frame:** কানেকশনের বিভিন্ন প্যারামিটার (যেমন: ম্যাক্সিমাম ফ্রেম সাইজ, উইন্ডো সাইজ) বিনিময় করে।

### 3. HPACK: আধুনিক হেডার কম্প্রেশন

- সাধারণ টেক্সট কম্প্রেশন (Gzip) হেডারে চালালে **CRIME Attack** নামক ক্রিপ্টোগ্রাফিক দুর্বলতা দেখা দেয়, তাই HTTP/2-এর জন্য একটি বিশেষায়িত অ্যালগরিদম **HPACK (RFC 7541)** তৈরি করা হয়।
- **Static Table:** ৬১টি বহুল ব্যবহৃত হেডার (যেমন: `:method: GET`, `:path: /`, `status: 200`) প্রি-ডিফাইন্ড টেবিলে সংরক্ষিত থাকে। সার্ভারে পুরো টেক্সট না পাঠিয়ে মাত্র ১টি ইনডেক্স নম্বর পাঠালেই সার্ভার পুরো হেডার বুঝে নেয়।
- **Dynamic Table:** কানেকশন চলাকালীন ক্লায়েন্ট ও সার্ভার উভয়েই নতুন দেখা হেডারগুলোকে মেমোরিতে টেবিল আকারে জমায়। ২য় রিকোয়েস্টে বিশাল `User-Agent` বা কুকি আবার পাঠানোর দরকার হয় না; কেবল তার টেবিল রেফারেন্স পাঠালেই চলে।
- **ফল:** হেডার সাইজ গড়ে ১,০০০ বাইট থেকে মাত্র **২০-৩০ বাইটে** নেমে আসে (৯৮% ব্যান্ডউইথ সাশ্রয়)!

---

### 4. The Achilles' Heel: TCP-Level Head-of-Line Blocking

HTTP/2 অ্যাপ্লিকেশন লেভেলের ব্লকিং দূর করলেও ট্রান্সপোর্ট লেভেলের কারণে একটি মারাত্মক দুর্বলতায় ভোগে:
- সমস্ত স্ট্রিম **একটিমাত্র একক TCP কানেকশনের** ভেতর দিয়ে চলে।
- যদি নেটওয়ার্কে সামান্য **২% প্যাকেট লস** থাকে:
  - টিসিপি একটি অবিচ্ছিন্ন বাইট স্ট্রিম গ্যারান্টি দেয়। ফলে ওই ড্রপ হওয়া টিসিপি প্যাকেট রিট্রান্সমিট না হওয়া পর্যন্ত ওএস কার্নেল সমস্ত ডেটা আটকে রাখে।
  - ফলস্বরূপ, একক কানেকশনে চলা **১০০টি এইচটিটিপি স্ট্রিমের সবকটি একসাথে থমকে দাঁড়ায়!**
- **বাস্তব ফলাফল:** দুর্বল ওয়াইফাই বা সেলুলার নেটওয়ার্কে প্যাকেট লস বাড়লে HTTP/2 অনেক সময় পুরনো HTTP/1.1-এর চেয়েও স্লো হয়ে যায়! (এই সমস্যাটি চিরতরে সমাধান করতেই পরবর্তীতে **HTTP/3 ও QUIC** তৈরি হয়)।

### 5. Alternatives & Evolution Comparison Matrix

| বৈশিষ্ট্য | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| **এনকোডিং** | প্লেইন টেক্সট (ASCII) | **বাইনারি ফ্রেমিং** | বাইনারি ফ্রেমিং |
| **কানেকশন সংখ্যা** | ডোমেন প্রতি ৬টি TCP | **হোস্ট প্রতি ১টি একক TCP** | হোস্ট প্রতি ১টি একক UDP (QUIC) |
| **মাল্টিপ্লেক্সিং** | ❌ নেই (HoL Blocking) | ✅ **ট্রু মাল্টিপ্লেক্সিং** | ✅ ট্রু মাল্টিপ্লেক্সিং |
| **হেডার কম্প্রেশন** | ❌ নেই | ✅ **HPACK** | ✅ QPACK |
| **TCP HoL Blocking** | কেবল একক কানেকশনে | ❌ **মারাত্মক ঝুঁকিপূর্ণ (প্যাকেট লসে)** | ✅ সম্পূর্ণ মুক্ত |
| **সার্ভার পুশ** | নেই | ⚠️ স্পেসিফিকেশনে ছিল (এখন বিলুপ্ত) | নেই |

### 6. Senior / Staff Engineer Interview Defense

> **ইন্টারভিউয়ার:** *"HTTP/2 Server Push কেন ডিজাইন করা হয়েছিল এবং কেন আধুনিক ওয়েব আর্কিটেকচারে (যেমন Chrome 106+) এটি পুরোপুরি অকেজো ও বাতিল (Deprecated) হয়ে গেল?"*
>
> 💡 **Staff-Level উত্তরের কাঠামো:**
> "HTTP/2 Server Push-এর উদ্দেশ্য ভালো ছিল কিন্তু বাস্তব বাস্তবায়ন ছিল চরম ত্রুটিপূর্ণ:
> 1. **মূল দর্শন:** ব্রাউজার যখন `/index.html` চায়, সার্ভার জানে যে ব্রাউজারের একটু পরেই `/style.css` লাগবে। তাই ব্রাউজার চাওয়ার আগেই সার্ভার নিজেই পুশ করে ডেটা পাঠিয়ে দিত যাতে ১টি RTT বাঁচে।
> 2. **কেন এটি ব্যর্থ হলো (The Fatal Flaws):**
>    - **ক্যাশ ব্লাইন্ডনেস (Cache Blindness):** সার্ভার জানে না ব্রাউজারের লোকাল ডিস্ক ক্যাশে ফাইলটি ইতিমধ্যে সেভ আছে কিনা! ফলে ব্রাউজারের কাছে ফাইলটি আগে থেকেই থাকা সত্ত্বেও সার্ভার জোর করে পুনরায় কয়েক মেগাবাইট ফাইল পুশ করে মূল্যবান মোবাইল ব্যান্ডউইথ নষ্ট করত।
>    - **ব্যান্ডউইথ কনটেনশন:** ক্রিটিক্যাল এইচটিএমএল প্রসেস করার আগেই পুশ করা সিএসএস/জেএস এসে ব্যান্ডউইথ দখল করে ফার্স্ট-কন্টেন্টফুল-পেইন্ট (FCP) উল্টো পিছিয়ে দিত।
> 3. **আধুনিক ও শ্রেষ্ঠ বিকল্প (Early Hints):** ইন্ডাস্ট্রি এখন সার্ভার পুশ বাতিল করে **103 Early Hints** গ্রহণ করেছে। সার্ভার ব্যাকএন্ড ডাটাবেজ প্রসেসিংয়ের সময়ই ব্রাউজারকে একটি হালকা স্ট্যাটাস `103` পাঠিয়ে দেয় যাতে ব্রাউজার নিজেই ডিস্ক ক্যাশ দেখে প্রয়োজনে প্যারালালে প্রি-লোড রিকোয়েস্ট পাঠাতে পারে।"

## 🔑 Answer Key & Self-Test Evaluation

<details>
<summary>👉 <b>Answer Key ও সমাধান দেখতে এখানে ক্লিক করুন</b></summary>

1. **সংজ্ঞা:** বাইনারি ফ্রেমিং ও মাল্টিপ্লেক্সিং সমৃদ্ধ হাই-পারফরম্যান্স প্রোটোকল; এটি গুগলের SPDY প্রোটোকল থেকে তৈরি।
2. **Binary Framing:** টেক্সটের বদলে ডেটাকে বাইনারি ফ্রেম ও স্ট্রিমে ভাগ করা, যা কম্পিউটারের পক্ষে দ্রুত পার্স করা যায় এবং সমান্তরালে মিশিয়ে দেওয়া যায়।
3. **Stream Multiplexing:** একক টিসিপি কানেকশনের ভেতর দিয়ে একাধিক স্বাধীন রিকোয়েস্ট ও রেসপন্স ফ্রেম বাই ফ্রেম ইন্টারলিভ করে পাঠানো।
4. **HPACK:** স্ট্যাটিক ও ডাইনামিক টেবিল দিয়ে ইনডেক্সিং; Gzip-এ CRIME ক্রিপ্টোগ্রাফিক আক্রমণ সম্ভব ছিল বলে নিরাপদ ডেডিকেটেড কম্প্রেশন তৈরি করা হয়।
5. **HTTPS বাধ্যবাধকতা:** তাত্ত্বিকভাবে ক্লিয়ারটেক্সট (h2c) স্পেকে থাকলেও সমস্ত প্রধান ব্রাউজার শুধুমাত্র TLS-এর ওপরেই HTTP/2 চালায়।
6. **TCP HoL Blocking in H2:** একক কানেকশনের ১টি প্যাকেট হারালে টিসিপি কার্নেল সমস্ত স্ট্রিমকে আটকে রাখে, ফলে উচ্চ প্যাকেট লসে সব রিকোয়েস্ট একসাথে স্লো হয়।
7. **Stream Priority:** ব্রাউজার জানাতে পারে কোন ফ্রেমটি আগে দরকার (যেমন: CSS আগে, ফুটার ইমেজ পরে), সার্ভার সেই অগ্রাধিকার মেনে ফ্রেম পাঠায়।
8. **Server Push ব্যর্থতা:** ব্রাউজার ক্যাশ জানে না বলে অপ্রয়োজনীয় ফাইল পুশ করত এবং ক্রিটিক্যাল এইচটিএমএল-এর ব্যান্ডউইথ কেড়ে নিত।
9. **103 Early Hints:** সার্ভার ব্যাকএন্ড রেন্ডারিংয়ের আগেই `103` কোডে লিঙ্ক হেডার পাঠিয়ে ব্রাউজারকে নির্দেশ দেয় কী কী ফাইল ব্রাউজারের লাগবে, ফলে ব্রাউজার ক্যাশ চেক করে নিজে প্রি-ফেচ করতে পারে।
10. **gRPC-তে HTTP/2:** বাইনারি ফ্রেমিং, মাল্টিপ্লেক্সিং, ফুল-ডুপ্লেক্স বাইডাইরেকশনাল স্ট্রিমিং এবং ট্রেইলার্স (Trailers) সাপোর্টের কারণে।
11. **Concurrent Streams:** ডিফল্ট সাধারণত ১০০ বা ১২৮। খুব বেশি বাড়ালে সার্ভারের মেমোরি ও কনটেনশন বাড়ে, খুব কম হলে ক্লায়েন্ট ব্লক হয়।
12. **HPACK Table Bomb:** আক্রমণকারী ইচ্ছাকৃতভাবে বিশাল ডাইনামিক টেবিল রিকোয়েস্ট তৈরি করে মেমোরি শেষ করে। সার্ভারে `SETTINGS_HEADER_TABLE_SIZE` (সাধারণত ৪ কেবি) কঠোরভাবে বাউন্ডেড রাখতে হয়।
13. **Bundling Anti-pattern:** মেগা বান্ডিলে এক লাইনের কোড বদলালে পুরো বিশাল ফাইল রি-ডাউনলোড করতে হয়; ছোট মডুলার ফাইল আলাদা রাখলে ব্রাউজার শুধু পরিবর্তিত ফাইলটি রি-ফেচ করে বাকিগুলো ক্যাশ থেকে নেয়।
14. **ALPN:** টিসিপি শেষ করে টিএলএস `ClientHello`-র ভেতরেই ব্রাউজার ঘোষণা করে সে `h2` সমর্থন করে, আলাদা কোনো রাউন্ড-ট্রিপ নষ্ট না করেই প্রোটোকল চূড়ান্ত হয়।
15. **H2 to H1.1 Bridging:** এজ প্রক্সিকে HTTP/2 থেকে আসা শত শত মাল্টিপ্লেক্সড ফ্রেম মেমোরিতে বাফার করে পেছনের সার্ভারের জন্য আলাদা আলাদা পৃথক টিসিপি সকেটে কনভার্ট করতে হয়, যা প্রক্সির মেমোরি ও সিপিইউ ওভারহেড বাড়ায়।
