## 📖 Deep Dive Notes

### 1. সহজ সংজ্ঞা ও Intuitive Mental Model

একটি নেটওয়ার্ক বা ব্যাকএন্ড সিস্টেমে নির্দিষ্ট সময়সীমার মধ্যে (যেমন: প্রতি সেকেন্ডে বা প্রতি মিনিটে) একজন নির্দিষ্ট ক্লায়েন্ট, আইপি অ্যাড্রেস বা এপিআই কি সর্বোচ্চ কতটি রিকোয়েস্ট পাঠাতে পারবে—তা কঠোরভাবে নিয়ন্ত্রণ ও সীমিত করার কৌশলকে **Rate Limiting** বলে।

সীমা অতিক্রম করলে সার্ভার রিকোয়েস্টটি রিজেক্ট করে ক্লায়েন্টকে **HTTP 429 Too Many Requests** স্ট্যাটাস কোড প্রদান করে।

```
[ Clients ] ─── 1000 Requests/sec ───> [ RATE LIMITER ] ─── 100 Req/sec ───> [ Backend API ]
                                       │ (Allowed: 100)
                                       └── (Dropped: 900 -> Return 429)
```

> 🧠 **Intuitive Mental Model (নাইটক্লাবের বাউন্সার অ্যানালজি):**
> একটি জনপ্রিয় নাইটক্লাবে একসঙ্গে সর্বোচ্চ ১০০ জন মানুষ থাকতে পারে। দরজায় একজন সতর্ক বাউন্সার দাঁড়িয়ে আছেন (**Rate Limiter**)। 
> বাইরে ২০০ জন মানুষ একসাথে ধাক্কাধাক্কি করলেও বাউন্সার প্রতি মিনিটে মাত্র ৫ জনকে ভেতরে ঢুকতে দেন। বাকিদের তিনি বাইরে অপেক্ষা করতে বলেন (**Throttling**)। বাউন্সার না থাকলে ক্লাবটি অতিরিক্ত মানুষের চাপে ভেঙে পড়ত!

### 2. রেট লিমিটিং অ্যালগরিদমসমূহের গভীর তুলনা

```
1. Token Bucket:       2. Leaky Bucket:        3. Sliding Window Counter:
   ┌───────────┐          ┌───────────┐           [Past 60s Window]
   │ Refill:   │          │ Incoming  │           |   Prev Min  |  Curr Min   |
   │ +Tokens   │          │ Spikes    │           | [30 reqs]   | [15 reqs]   |
   │ ⬤ ⬤ ⬤ ⬤   │          │ ░░░░░░░░░ │           └─────────────┴─────────────┘
   └─────┬─────┘          └─────┬─────┘           Weight = (60 - elapsed) / 60
         ▼                      ▼                 Estimated = (30 * W) + 15
    Burst Allowed         Constant Rate
```

| অ্যালগরিদম | কীভাবে কাজ করে | সুবিধা | অসুবিধা / কখন ব্যবহার করবেন |
|---|---|---|---|
| **Token Bucket** | নির্দিষ্ট হারে বাকেটে টোকেন যোগ হয়। প্রতি রিকোয়েস্টে ১টি টোকেন কাটে। | বাকেটে টোকেন থাকলে আকস্মিক ট্রাফিক স্পাইক (Burst) চমৎকারভাবে হ্যান্ডেল করতে পারে। | টোকেন কাউন্ট ও রিফিল স্টেট ট্র্যাক করতে হয়। AWS ও Google API-র ডিফল্ট পছন্দ। |
| **Leaky Bucket** | ট্রাফিক যেকোনো স্পিডে ঢুকুক না কেন, বাকেটের তলার ছিদ্র দিয়ে একদম ফিক্সড স্মুথ গতিতে আউটপুট বের হয়। | ট্রাফিককে সম্পূর্ণ কনস্ট্যান্ট ও প্রিডিক্টেবল স্ট্রিম বানায়। | বাকেট ফুল হলে অতিরিক্ত স্পাইকের দরকারী রিকোয়েস্টগুলো তৎক্ষণাৎ ড্রপ করে। |
| **Fixed Window Counter** | প্রতি ৬০ সেকেন্ডের একটি স্থির টাইম উইন্ডো থাকে (যেমন: ১২:০১-১২:০২)। উইন্ডোতে কাউন্টার বাড়ে। | মেমোরি খরচ সর্বনিম্ন (সিঙ্গেল ইন্টিজার কাউন্টার)। | **Window Boundary Spike:** ১২:০১:৫৯ এ ১০০টি এবং ১২:০২:০১ এ ১০০টি রিকোয়েস্ট পাঠিয়ে মাত্র ২ সেকেন্ডে ডাবল লোড ফেলা যায়! |
| **Sliding Window Log** | প্রতিটি রিকোয়েস্টের সুনির্দিষ্ট টাইমস্ট্যাম্প একটি লগ বা সেটে (Redis ZSET) সংরক্ষণ করে গত ৬০ সেকেন্ডের কাউন্ট মেপে দেখে। | শতভাগ নিখুঁত গাণিতিক নিয়ন্ত্রণ। | প্রতিটি রিকোয়েস্টের টাইমস্ট্যাম্প স্টোর করায় মেমোরি খরচ অতিরিক্ত বেশি। |
| **Sliding Window Counter** | পূর্ববর্তী উইন্ডো এবং বর্তমান উইন্ডোর কাউন্টারকে সময়ের অনুপাতিক ওয়েট (Weight) দিয়ে গুণ করে একটি এস্টিমেট করে। | অত্যন্ত কম মেমোরি খরচে প্রায় ৯৯.৯% নিখুঁত ফলাফল দেয়। | অতি সূক্ষ্ম গাণিতিক সামান্য ওঠানামা হতে পারে ($<0.05\%$), তবে প্রোডাকশনের জন্য শ্রেষ্ঠ (Cloudflare-এর পছন্দ)। |

### 3. Production Architecture: Distributed Redis Rate Limiting

একটি একক সার্ভারে মেমোরি কাউন্টার রাখা সহজ হলেও, যখন ব্যাকএন্ডে ৫০টি এপিআই গেটওয়ে নোড থাকে তখন সেন্ট্রালাইজড ডিস্ট্রিবিউটেড রেট লিমিটিং প্রয়োজন:

```
[ Client Request ] ──> [ API Gateway Node 1..N ]
                               │
                               │ Atomic Lua Script Execution
                               ▼
                    [ Central Redis Cluster ]
               (Evals Token Bucket or Sliding Window)
```

#### কেন Redis Lua Script অপরিহার্য?
সাধারণভাবে ক্লায়েন্ট রিকোয়েস্টে Redis থেকে কাউন্টার রিড করা (`GET`), কোডে চেক করা এবং তারপর ইনক্রিমেন্ট করা (`INCR`) একটি মারাত্মক **Race Condition** তৈরি করে।
Redis-এ একটি **Lua Script** পাঠালে সেটি সম্পূর্ণ **Atomic** ভাবে এক্সিকিউট হয়; মাঝখানে অন্য কোনো রিকোয়েস্ট ঢুকতে পারে না:

```lua
-- Atomic Sliding Window Counter in Redis Lua
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local current = tonumber(redis.call('get', key) or "0")

if current + 1 > limit then
    return 0 -- Rejected (Rate limited)
else
    redis.call("INCRBY", key, 1)
    if current == 0 then
        redis.call("EXPIRE", key, 60)
    end
    return 1 -- Allowed
end
```

### 4. HTTP Headers Standard (RFC 6585)

রেট লিমিটার ক্লায়েন্টকে রেসপন্সে পরিষ্কার তথ্য জানাবে:
```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 30
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1693500000

{
  "error": "Rate limit exceeded. Please retry after 30 seconds."
}
```

### 5. Failure Modes & Production Mitigations

#### Failure Mode 1: Central Redis Becomes Bottleneck or Crashes
- **ঝুঁকি:** প্রতি রিকোয়েস্টে Redis-এ নেটওয়ার্ক কল করার কারণে Redis স্যাচুরেটেড হয়ে যায় অথবা Redis ক্র্যাশ করলে পুরো এপিআই গেটওয়ে রিকোয়েস্ট ড্রপ করতে শুরু করে।
- **প্রতিরোধ (Mitigation):** **Fail-Open Strategy & Local In-Memory Batching:** Redis ডাউন হয়ে গেলে রেট লিমিটার "Fail-Open" নীতিতে সমস্ত ট্রাফিককে পাস হতে দেবে (কারণ রেট লিমিটার ডাউন হওয়ার চেয়ে পুরো ব্যবসা বন্ধ হওয়া বেশি ক্ষতিকর)। গেটওয়ে নোডগুলো তাদের মেমোরিতে ৫ সেকেন্ডের রিকোয়েস্ট ব্যাচ করে তারপর Redis-এ সিঙ্ক করবে।

### 6. Senior / Staff Engineer Interview Defense

> **ইন্টারভিউয়ার:** *"লাখ লাখ ইউজারের সিস্টেমে রেট লিমিটিংয়ের জন্য আপনি কোন অ্যালগরিদম এবং কী ধরণের ইনফ্রাস্ট্রাকচার আর্কিটেকচার বেছে নেবেন?"*
>
> 💡 **Staff-Level উত্তরের কাঠামো:**
> "আমরা একটি বহুস্তরীয় (Multi-tier) রেট লিমিটিং আর্কিটেকচার প্রয়োগ করব:
> 1. **অ্যালগরিদম নির্বাচন (Sliding Window Counter):** আমরা ফিক্সড উইন্ডোর বাউন্ডারি স্পাইক এড়াতে এবং স্লাইডিং লগের বিশাল মেমোরি খরচ বাঁচাতে **Sliding Window Counter** বেছে নেব, যা মেমোরি-সাশ্রয়ী ও অত্যন্ত নিখুঁত।
> 2. **টিয়ার ১ - Edge WAF (Cloudflare/AWS WAF):** ক্ষতিকর বট, DDoS এবং ব্রুট-ফোর্স আক্রমণকারী আইপিগুলোকে আমাদের ক্লাউড ডেটাসেন্টারে পৌঁছানোর আগেই ক্লাউড এজে ব্লক করা হবে।
> 3. **টিয়ার ২ - API Gateway with Redis Cluster:** ভ্যালিড অথেনটিকেটেড ইউজারদের পার-টিয়ার লিমিটিংয়ের জন্য এপিআই গেটওয়েতে Redis ক্লাস্টার এবং **Atomic Lua Scripts** চালাব।
> 4. **রেজিলিয়েন্স ও হাই-থ্রুপুট অপ্টিমাইজেশন:** প্রতি কলে Redis নেটওয়ার্ক রাউন্ড-ট্রিপ এড়াতে আমরা লোকাল মেমোরি টোকেন বাকেট চালাব এবং প্রতি ১ সেকেন্ড পর পর Redis-এর সাথে অ্যাসিঙ্ক্রোনাসলি টোকেন সিঙ্ক করব। Redis ক্লাস্টার কখনো ক্র্যাশ করলে সিস্টেম **Fail-Open** মোডে যাবে যাতে কোনো ভ্যালিড গ্রাহকের লেনদেন ব্যাহত না হয়।"

5. `Retry-After` এবং `X-RateLimit-Remaining` হেডারের কাজ কী?

### Intermediate Practice Questions
6. Leaky Bucket এবং Token Bucket-এর মধ্যকার মূল প্রযুক্তিগত পার্থক্য কী?

8. ডিস্ট্রিবিউটেড রেট লিমিটিংয়ে রেস কন্ডিশন দূর করতে Redis Lua Script কেন অপরিহার্য?
9. যদি সেন্ট্রালাইজড Redis ক্লাস্টার ডাউন হয়ে যায়, তবে রেট লিমিটারের কি Fail-Open হওয়া উচিত নাকি Fail-Closed? কেন?
10. আইপি-বেসড রেট লিমিটিংয়ের প্রধান ঝুঁকিগুলো (NAT, Corporate Proxy, Dynamic IPs) কী কী?

1. **সংজ্ঞা:** নির্দিষ্ট সময়ের মধ্যে রিকোয়েস্টের সংখ্যা সীমিত রাখা যাতে সিস্টেম ওভারলোড, অপব্যবহার ও সাইবার আক্রমণ থেকে রক্ষা পায়।
2. **স্ট্যাটাস কোড:** `HTTP 429 Too Many Requests`।
3. **Burst Traffic:** বাকেটে জমে থাকা অতিরিক্ত টোকেন দিয়ে স্বল্প সময়ের জন্য নির্ধারিত সীমার চেয়ে দ্রুত গতিতে রিকোয়েস্ট এক্সেপ্ট করার ক্ষমতা।
4. **Boundary Spike:** উইন্ডো পরিবর্তনের শেষ সেকেন্ড ও পরের উইন্ডোর প্রথম সেকেন্ডে ট্রাফিক ঢুকে সীমার দ্বিগুণ ট্রাফিক সিস্টেমে প্রবেশ করানো।
5. **হেডার্স:** `Retry-After` জানায় কত সেকেন্ড পর আবার রিকোয়েস্ট করা যাবে; `X-RateLimit-Remaining` জানায় বর্তমান উইন্ডোতে আর কতটি রিকোয়েস্ট বাকি আছে।
6. **Token vs Leaky:** Token বাকেট স্পাইক অ্যালাউ করে; Leaky বাকেট সমস্ত ট্রাফিককে কনস্ট্যান্ট ও স্মুথ একক গতিতে নির্গত করে।
7. **ZSET মেমোরি:** প্রতিটি রিকোয়েস্টের জন্য টাইমস্ট্যাম্প ও ইউনিক মেম্বার আইডি স্টোর করতে হয়। লাখ লাখ রিকোয়েস্টে গিগাবাইট মেমোরি খরচ হয়।
8. **Lua Script গুরুত্ব:** রিড ও রাইট অপারেশনকে একটি একক অ্যাটমিক ট্রানজ্যাকশনে পরিণত করে, ফলে একাধিক গেটওয়ের কনকারেন্ট রিকোয়েস্টে রেস কন্ডিশন ঘটে না।
9. **Fail-Open vs Closed:** সাধারণ ওয়েব ট্রাফিকে Fail-Open শ্রেয়, কারণ রেট লিমিটার নষ্ট হলে সাময়িক রিকোয়েস্ট ছেড়ে দেওয়া ভালো কিন্তু সমস্ত আসল ইউজারের সার্ভিস বন্ধ করা অগ্রহণযোগ্য।
10. **IP Limiting ঝুঁকি:** একটি অফিসের শত শত কর্মী একটি পাবলিক আইপি শেয়ার করায় একজন ক্ষতিকর হলে পুরো অফিস ব্লক হয়ে যায়; আবার আক্রমণকারী সহজে প্রক্সি আইপি বদলে আক্রমণ চালাতে পারে।
11. **Local Batching:** গেটওয়ে নোড লোকাল মেমোরিতে টোকেন রাখে এবং প্রতি ১ সেকেন্ড পর পর ব্যাচে রেডিসে ডেটা লেখে, ফলে রেডিসের ওপর রিকোয়েস্ট চাপ ৯৯% কমে যায়।
12. **Multi-tenant Priority:** টায়ার ভিত্তিক বাকেট সাইজ নির্ধারণ (Enterprise: 10,000/s, Free: 100/s)। ওভারলোডে ফ্রি টায়ারকে আগে থ্রোটল করে এন্টারপ্রাইজ ট্রাফিক রক্ষা করা।
13. **Adaptive Limiting:** স্ট্যাটিক লিমিট না রেখে সার্ভারের p99 ল্যাটেন্সি ৫০০ms ছাড়িয়ে গেলে বা সিপিইউ ৮০% হলে স্বয়ংক্রিয়ভাবে রেট লিমিট কমিয়ে সিস্টেম রক্ষা করা।
14. **Multi-dimensional Rules:** রুটের টাইপ (GET বনাম POST) এবং ইউজার রোলের ওপর ভিত্তি করে একাধিক আলাদা কি তৈরি করা (`rate:user_id:read` এবং `rate:user_id:write`)।
15. **Client-side Backoff:** ৪২৯ এরর পেলে ক্লায়েন্ট লাইব্রেরি `Retry-After` হেডার অনুসরণ করে এবং এক্সপোনেনশিয়াল ব্যাকঅফ ও র‍্যান্ডম জিটার যোগ করে পুনরায় চেষ্টা করে যাতে থান্ডারিং হার্ড না ঘটে।
