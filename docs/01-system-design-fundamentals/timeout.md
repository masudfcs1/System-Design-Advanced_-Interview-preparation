## 📖 Deep Dive Notes

### 1. সহজ সংজ্ঞা ও Intuitive Mental Model

ডিস্ট্রিবিউটেড সফটওয়্যার ইঞ্জিনিয়ারিংয়ে **Timeout** হলো এমন একটি পূর্বনির্ধারিত সর্বোচ্চ সময়সীমা, যার মধ্যে কোনো নেটওয়ার্ক অপারেশন বা ডিপেন্ডেন্সি কলের রেসপন্স না আসলে ক্লায়েন্ট অনন্তকাল অপেক্ষা না করে অবিলম্বে সংযোগ ছিন্ন করে এবং ত্রুটি ঘোষণা করে নিজের রিসোর্স (থ্রেড, সকেট, মেমোরি) মুক্ত করে দেয়।

> 🧠 **Intuitive Mental Model (বন্ধুর জন্য অপেক্ষা অ্যানালজি):**
> আপনি এক বন্ধুর সাথে সিনেমা দেখার জন্য বিকাল ৫টায় হলের সামনে দেখা করার কথা বললেন।
> - **কোনো টাইমআউট না থাকলে (Infinite Timeout):** বন্ধু যদি ঘুমিয়ে থাকে বা পথিমধ্যে আটকে যায়, আপনি হয়তো সিনেমা শেষ হয়ে রাত ১২টা পর্যন্ত হলের সামনে দাঁড়িয়ে থাকবেন (**Thread Starvation / System Freeze**)! আপনার পুরো দিন নষ্ট হবে।
> - **১৫ মিনিটের টাইমআউট থাকলে (Timeout = 15 mins):** আপনি বিকাল ৫:১৫ পর্যন্ত অপেক্ষা করলেন। বন্ধু না আসায় আপনি টিকিট ক্যানসেল করে বাড়ি ফিরে অন্য কাজ শুরু করলেন (**Resource Reclaimed / Fail-Fast**)।

### 2. The 3 Types of Network Timeouts

নেটওয়ার্ক কলের বিভিন্ন পর্যায়ে ৩টি আলাদা টাইমআউট কনফিগার করতে হয়:

```
[ Client ] ─── TCP SYN ───> [ Server ]
     │ (1) Connection Timeout (TCP 3-Way Handshake)
     ▼
[ Client ] <── TCP ACK ──── [ Server ]
     │
     │ ─── HTTP Request Data ───>
     │
     │ (2) Socket / Read Timeout (Time between data packets)
     ▼
[ Client ] <── HTTP Response Data ── [ Server ]

     ◄──────────────── (3) Global Request Timeout ────────────────►
```

1. **Connection Timeout:** ক্লায়েন্ট ও সার্ভারের মধ্যে টিসিপি ৩-ওয়ে হ্যান্ডশেক (`SYN -> SYN-ACK -> ACK`) সম্পন্ন হতে সর্বোচ্চ কত সময় অপেক্ষা করা হবে (সাধারণত ১-৩ সেকেন্ড)। ফায়ারওয়ালের ব্ল্যাকহোল বা সার্ভার ডাউন থাকলে এটি ট্রিগার হয়।
2. **Socket / Read Timeout:** টিসিপি কানেকশন ওপেন হওয়ার পর সার্ভারের পাঠানো ডেটার দুটি প্যাকেটের মধ্যকার বিরতির সর্বোচ্চ সময়সীমা (যেমন: ৫ সেকেন্ড)। সার্ভার প্রসেসিংয়ে বা ডাটাবেজে আটকে থাকলে এটি ট্রিগার হয়।
3. **Global Request / Transaction Timeout:** পুরো এন্ড-টু-এন্ড রিকোয়েস্ট (হ্যান্ডশেক + ডেটা সেন্ড + সার্ভার এক্সিকিউশন + রেসপন্স রিড) শুরু থেকে শেষ হতে মোট সময়সীমা।

### 3. The "Silent Killer": Default Infinite Timeouts

জাভা (HttpURLConnection), পাইথন (Requests লাইব্রেরি) বা নোডজেসের মতো অনেক জনপ্রিয় প্ল্যাটফর্মের ডিফল্ট নেটওয়ার্ক টাইমআউট হলো **INFINITE (অসীম)!**
- যদি আপনার কোডে কোনো স্পষ্ট টাইমআউট কনফিগার না থাকে, এবং ডাউনস্ট্রিম কোনো সার্ভিস হেভি লোডে আটকে গিয়ে রেসপন্স না পাঠায়—
- আপনার সার্ভারের থ্রেডগুলো অনন্তকাল অপেক্ষা করবে!
- মাত্র ৫ মিনিটের মধ্যে সমস্ত টমক্যাট/জেভিএম থ্রেড নিঃশেষ হয়ে আপনার নিজস্ব সার্ভিস শতভাগ ক্র্যাশ করবে।
- **গোল্ডেন রুল:** প্রতিটি আউটগোয়িং নেটওয়ার্ক কলেই অবশ্যই একটি সুনির্দিষ্ট কঠোর টাইমআউট থাকতে হবে!

### 4. Distributed Deadlines & Context Cancellation (এন্ড-টু-এন্ড ডেডলাইন)

মাইক্রোসার্ভিস চেইনে সাধারণ ফিক্সড টাইমআউট একটি ভয়াবহ "Wasted Work" সমস্যা তৈরি করে:

```
Without Deadlines:
Client (Timeout: 2s) ──> Service A (Timeout: 5s) ──> Service B (Timeout: 10s)
Time: 2.1 seconds passes!
- Client timed out and left! (User closed browser)
- But Service A and B are STILL running heavy database queries for the next 8 seconds!
- Enormous CPU and DB resources completely WASTED on a ghost request!
```

#### সমাধান: Distributed Deadline Propagation (gRPC / OpenTelemetry)
- ক্লায়েন্ট রিকোয়েস্ট পাঠানোর সময় একটি পরম সময়সীমা (Absolute Deadline: "12:00:05.000") হেডারে পাস করে (`grpc-timeout: 2000m`)।
- সার্ভিস A সার্ভিস B-কে কল করার সময় অবশিষ্ট সময় হিসাব করে ডেডলাইন কমিয়ে পাঠায়।
- ক্লায়েন্ট ২ সেকেন্ডে টাইমআউট হয়ে সকেট ক্লোজ করলে, gRPC Context Cancellation তাৎক্ষণিকভাবে সার্ভিস A এবং B-এর সমস্ত প্রসেস বন্ধ (Abort) করে দেয়।

### 5. গাণিতিকভাবে কীভাবে অপটিমাল টাইমআউট নির্ধারণ করবেন?

অনুমান করে (Guesswork) টাইমআউট বসানো ভুল। টাইমআউট নির্ধারণের বৈজ্ঞানিক সূত্র:

$$\mathbf{\text{Timeout} = \text{p99 Latency of Dependency} + (3 \times \text{Standard Deviation})}$$

বাস্তব স্ট্যান্ডার্ড:
- যদি একটি পেমেন্ট গেটওয়ের p99 ল্যাটেন্সি হয় ৮০০ms এবং p99.9 হয় ১.২ সেকেন্ড:
- টাইমআউট **১.৫ সেকেন্ড থেকে ২ সেকেন্ড** নির্ধারণ করা উচিত।
- টাইমআউট খুব কম বসালে (যেমন ৬০০ms) সুস্থ স্বাভাবিক রিকোয়েস্টগুলোও মিথ্যা টাইমআউট (False Positives) পেয়ে ক্লায়েন্টে এরর দেখাবে।
- টাইমআউট খুব বেশি বসালে (যেমন ৩০ সেকেন্ড) সার্ভারের থ্রেডপুল আটকে গিয়ে ক্যাসকেডিং ফেইলিউর হবে।

### 6. Senior / Staff Engineer Interview Defense

> **ইন্টারভিউয়ার:** *"আমাদের সিস্টেমে একাধিক মাইক্রোসার্ভিসের মধ্য দিয়ে রিকোয়েস্ট যায়। ডাউনস্ট্রিমে ডেটাবেজ ও সিপিইউ অপচয় রোধে টাইমআউট কীভাবে আর্কিটেক্ট করবেন?"*
>
> 💡 **Staff-Level উত্তরের কাঠামো:**
> "আমরা শুধুমাত্র বিচ্ছিন্নভাবে প্রতিটা সার্ভিসে লোকাল সকেট টাইমআউট কনফিগার করব না; আমরা একটি **Distributed Deadline Propagation** আর্কিটেকচার প্রতিষ্ঠা করব:
> 1. **এন্ট্রি পয়েন্টে ডেডলাইন সেট:** এপিআই গেটওয়েতে রিকোয়েস্ট প্রবেশের সময় SLAs অনুযায়ী একটি বৈশ্বিক টাইম বাজেট (যেমন: `Total Deadline = 2.5s`) বরাদ্দ করা হবে।
> 2. **Context Propagation:** gRPC মেটাডাটা বা HTTP হেডার (`X-Request-Deadline: <timestamp>`) দিয়ে প্রতিটি মাইক্রোসার্ভিস চেইনে অবশিষ্ট সময় (Remaining Time Budget) প্রপাগেট হবে। কোনো সার্ভিস কল করার আগে চেক করবে হাতে পর্যাপ্ত সময় আছে কিনা ($>50$ms); না থাকলে সে ডাউনস্ট্রিমে কলই করবে না।
> 3. **Context Cancellation & Cooperative Abort:** ক্লায়েন্ট সকেট ড্রপ করলে বা সময় শেষ হলে Go Context বা gRPC Cancel সিগন্যাল পাঠিয়ে ব্যাকগ্রাউন্ডে চলতে থাকা সমস্ত ডাটাবেজ কুয়েরি (`pg_cancel_backend`) ও সিপিইউ টাস্ক তাৎক্ষণিকভাবে বন্ধ করে দেওয়া হবে যাতে কোনো ঘোস্ট প্রসেসিং না চলে।"

## 🔑 Answer Key & Self-Test Evaluation

<details>
<summary>👉 <b>Answer Key ও সমাধান দেখতে এখানে ক্লিক করুন</b></summary>

1. **টাইমআউট না থাকার ঝুঁকি:** সার্ভারের থ্রেডগুলো অনন্তকাল রেসপন্সের অপেক্ষায় আটকে থাকে এবং দ্রুত কানেকশন পুল শেষ হয়ে সিস্টেম সম্পূর্ণ ক্র্যাশ করে।
2. **Connection vs Socket:** Connection হলো টিসিপি হ্যান্ডশেকের সর্বোচ্চ সময়সীমা; Socket হলো কানেকশন হওয়ার পর ডেটা প্যাকেটের মধ্যকার সর্বোচ্চ বিলম্ব।
3. **ডিফল্ট টাইমআউট:** অনেক ক্লায়েন্টে (যেমন জাভা HttpURLConnection বা পাইথন Requests) এটি `Infinite` (শূন্য বা অনির্দিষ্টকাল)!
4. **খুব কম টাইমআউট:** সুস্থ স্বাভাবিক অপারেশনও মাঝেমধ্যে সাময়িক লোডে কয়েক মিলি-সেকেন্ড দেরি করলেই মিথ্যা এরর (False Positive) পেয়ে ড্রপ হবে।
5. **504 Gateway Timeout:** প্রক্সি বা গেটওয়ে পেছনের ব্যাকএন্ড সার্ভার থেকে নির্ধারিত সময়সীমার মধ্যে রেসপন্স না পেলে ক্লায়েন্টকে এই কোড দেয়।
6. **Distributed Deadline:** ক্লায়েন্ট একটি বৈশ্বিক ডেডলাইন পাঠায়। চেইনের যেকোনো স্তরে সময় শেষ হলে সাথে সাথে কন্টেক্সট ক্যানসেল হয়ে সমস্ত প্রসেস বন্ধ হয়ে যায়।
7. **Server-Still-Working:** ক্লায়েন্ট টাইমআউট পেয়ে চলে গেলেও সার্ভার ব্যাকগ্রাউন্ডে ভারী কুয়েরি চালিয়ে রিসোর্স নষ্ট করে। সমাধান: সকেট ক্লোজ ইভেন্ট শুনে সার্ভার কোড ইন্টারাপ্ট করা।
8. **গাণিতিক নির্ধারণ:** $\text{Timeout} = \text{p99} + (3 \times \text{StdDev})$। সাধারণত p99.9 ল্যাটেন্সির চেয়ে কিছুটা বেশি বাফার রাখা যাতে ফলস পজিটিভ ১% এর নিচে থাকে।
9. **চেইন টাইমআউট অর্ডারিং:** আপস্ট্রিমের টাইমআউট সবসময় ডাউনস্ট্রিমের মোট সময়ের চেয়ে বড় হতে হবে: $\text{Timeout}(A) > \text{Timeout}(B) + \text{Network Buffer}$। অন্যথায় B কাজ শেষ করার আগেই A টাইমআউট দিয়ে দেবে।
10. **DB Timeouts:** Connection Acquisition পুল থেকে কানেকশন পাওয়ার সীমা; Statement/Query Timeout হলো ডাটাবেজ সার্ভারে কুয়েরি এক্সিকিউট হওয়ার সর্বোচ্চ সীমা।
11. **Envoy Timeout Coordination:** Route Timeout হলো সম্পূর্ণ রিকোয়েস্টের মোট সময়সীমা (যেমন ৫ সেকেন্ড); Per-Try Timeout হলো প্রতিটি রিট্রাই চেষ্টার একক সময়সীমা (যেমন ১.৫ সেকেন্ড)।
12. **Long Operations:** ক্লায়েন্টকে তাৎক্ষণিক `202 Accepted` ও একটি `status_url` দিয়ে ব্যাকগ্রাউন্ডে কাজ পাঠানো। ক্লায়েন্ট পোল করবে বা ওয়েবহুক দিয়ে নোটিফিকেশন পাবে।
13. **TCP_USER_TIMEOUT:** কেবল ওএস লেভেলের আকনলেজমেন্ট না আসা পর্যন্ত অপেক্ষা না করে নির্দিষ্ট সময়ের মধ্যে আন-অ্যাকনলেজড ডেটা পেলে কার্নেল ফোর্সফুলি সকেট ডেড ঘোষণা করে।
14. **Reactive Timeout:** টাইমআউট অপারেটর আপস্ট্রিম সাবস্ক্রিপশন বাতিল করে কিন্তু আন্ডারলাইং নেটওয়ার্ক সকেট ড্রেন না হলে ব্যাকপ্রেশার বাফার লিক হতে পারে।
15. **2PC Timeout Reconciliation:** প্রিপেয়ার ফেজের পর টাইমআউট পেলে নোডগুলো প্যাক্সোস/রাফট বা ট্রানজ্যাকশন ম্যানেজারের স্টেট লগে কুয়েরি করে ডিসিশন নিশ্চিত করে।
