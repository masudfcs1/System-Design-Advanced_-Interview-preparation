## 📖 Deep Dive Notes

### 1. সহজ সংজ্ঞা ও Intuitive Mental Model

**Client-Server Architecture** হলো একটি ডিস্ট্রিবিউটেড কম্পিউটিং কাঠামো যা কাজের দায়িত্বকে দুটি প্রধান সত্ত্বার মধ্যে ভাগ করে দেয়:
1. **Client (সেবা গ্রহণকারী):** ইউজার ইন্টারফেস উপস্থাপন করে এবং রিকোয়েস্ট পাঠায় (যেমন: ওয়েব ব্রাউজার, মোবাইল অ্যাপ, ডেস্কটপ ক্লায়েন্ট, IoT ডিভাইস)।
2. **Server (সেবা প্রদানকারী):** কেন্দ্রীয়ভাবে বিজনেস লজিক এক্সিকিউট করে, নিরাপত্তা ও অথেনটিকেশন নিয়ন্ত্রণ করে এবং ডাটাবেজ এক্সেস পরিচালনা করে ক্লায়েন্টের রিকোয়েস্টে সাড়া দেয়।

```
┌─────────────────┐                                  ┌─────────────────┐
│     Client      │ ───── (1) Send Request ────────> │     Server      │
│  (Browser/App)  │ <──── (2) Return Response ────── │ (Business Logic)│
└─────────────────┘                                  └────────┬────────┘
                                                              │
                                                              ▼
                                                     ┌─────────────────┐
                                                     │    Database     │
                                                     └─────────────────┘
```

> 🧠 **Intuitive Mental Model (রেস্তোরাঁর গ্রাহক ও বাবুর্চি অ্যানালজি):**
> আপনি একটি আধুনিক রেস্তোরাঁয় খেতে গেলেন। 
> - আপনি হলেন **Client**; আপনি মেন্যু দেখে ওয়েটারকে খাবারের অর্ডার দিলেন (**Request**)। 
> - কিচেনে থাকা অভিজ্ঞ শেফ হলেন **Server**; তিনি কাঁচামাল (Database) থেকে রেসিপি অনুযায়ী রান্না সম্পন্ন করে ওয়েটারের মাধ্যমে আপনার টেবিলে সাজিয়ে দেন (**Response**)। 
> - কোনো গ্রাহককে কিচেনের ভেতরে ঢুকতে দেওয়া হয় না (**Security & Encapsulation**)। শেফ কীভাবে গ্যাস বা ওভেন ব্যবহার করছেন তা গ্রাহকের জানার দরকার নেই—গ্রাহক কেবল চূড়ান্ত খাবারটি উপভোগ করেন (**Abstraction**)।

### 2. Tiered Evolution: 2-Tier, 3-Tier, ও N-Tier Architecture

```
2-Tier (Client-Server):
[ Rich Desktop Client (Business Logic) ] ──> [ Database Server ]

3-Tier (Modern Enterprise Web):
[ Client (UI) ] ──> [ Application Server (Logic) ] ──> [ Database Server (Data) ]

N-Tier (Cloud-Native Scale):
[ Client ] ──> [ CDN / WAF ] ──> [ API Gateway ] ──> [ Microservices ] ──> [ Distributed DB / Cache ]
```

1. **2-Tier Architecture:** পুরনো ডেস্কটপ অ্যাপ যেখানে ক্লায়েন্ট নিজেই বিজনেস লজিক রান করত এবং সরাসরি ডেটাবেজে SQL কুয়েরি পাঠাত। মারাত্মক সিকিউরিটি ঝুঁকি এবং স্কেলেবিলিটির অভাব।
2. **3-Tier Architecture:** ওয়েবের স্ট্যান্ডার্ড রূপ—Presentation Tier (Frontend), Application/Logic Tier (Backend Server), এবং Data Tier (Database)। এটি Separation of Concerns নিশ্চিত করে।
3. **N-Tier Architecture:** উচ্চ স্কেলে ক্যাশিং লেয়ার (Redis), মেসেজ ব্রোকার (Kafka), অথেনটিকেশন গেটওয়ে এবং মাইক্রোসার্ভিস যুক্ত হয়ে একাধিক স্তরে বিভক্ত হয়।

### 3. Thin Client vs Thick (Rich) Client

| বৈশিষ্ট্য | Thin Client (হালকা ক্লায়েন্ট) | Thick / Rich Client (ভারী ক্লায়েন্ট) |
|---|---|---|
| **প্রসেসিং অবস্থান** | প্রায় ৯৫% লজিক সার্ভারে চলে; ক্লায়েন্ট শুধু HTML রেন্ডার করে | প্রচুর বিজনেস লজিক, স্টেট ও ক্যাশিং ক্লায়েন্টে চলে (React SPA, Mobile App) |
| **অফলাইন সাপোর্ট** | অফলাইনে কিছুই কাজ করে না | লোকাল SQLite/IndexedDB দিয়ে চমৎকার অফলাইন মোড কাজ করে |
| **ব্যান্ডউইথ ব্যবহার** | প্রতি পেজে সার্ভার-রেন্ডার্ড ডেটা ও মার্কআপ পাঠাতে হয় | শুধু কাঁচা JSON ডেটা এপিআই দিয়ে আদান-প্রদান হয় (কম ব্যান্ডউইথ) |
| **সিকিউরিটি জটিলতা** | অত্যন্ত সুরক্ষিত (ক্লায়েন্টের হাতে কোড বা লজিক থাকে না) | ক্লায়েন্ট কোড টেম্পারিং ও রিভার্স ইঞ্জিনিয়ারিংয়ের ঝুঁকি থাকে |

### 4. Client-Server বনাম Peer-to-Peer (P2P)

```
Client-Server (Centralized):             Peer-to-Peer (Decentralized):
       [ Server ]                               [ Peer A ] ─────── [ Peer B ]
      ┌────┼────┐                                   │  \       /  │
      ▼    ▼    ▼                                   │    \   /    │
    [C1]  [C2]  [C3]                                │      X      │
                                                    │    /   \    │
(সেন্ট্রাল সার্ভার ডাউন মানে সব শেষ)                 [ Peer C ] ─────── [ Peer D ]
                                           (প্রতিটি নোড একই সাথে ক্লায়েন্ট ও সার্ভার)
```

| প্যারামিটার | Client-Server Architecture | Peer-to-Peer Architecture (BitTorrent, Bitcoin) |
|---|---|---|
| **নিয়ন্ত্রণ** | সেন্ট্রালাইজড (একক কর্তৃপক্ষ বা কোম্পানি) | ডিসেন্ট্রালাইজড (কোনো একক মালিক নেই) |
| **স্কেলিং খরচ** | সার্ভারের ব্যান্ডউইথ ও ক্লাউড খরচ ব্যবহারকারী বাড়ার সাথে সাথে বাড়ে | ব্যবহারকারী বাড়লে সামগ্রিক ডাউনলোড ব্যান্ডউইথ বাড়ে (স্বয়ংক্রিয় স্কেলিং) |
| **সিকিউরিটি ও প্রাইভেসি** | সার্ভারে সমস্ত ডেটা সংরক্ষিত; সেন্ট্রাল অডিট সম্ভব | বাইজেন্টাইন ফল্ট টলারেন্স ও কনসেনসাস অ্যালগরিদম প্রয়োজন |

### 5. Failure Modes & Security Principles

#### গোল্ডেন সিকিউরিটি রুল: "Never Trust the Client!"
- **ঝুঁকি:** মোবাইল অ্যাপ বা ব্রাউজারে ইনপুট ভ্যালিডেশন থাকলেও একজন ক্ষতিকর ব্যবহারকারী Postman বা `curl` দিয়ে সরাসরি ভুল বা ক্ষতিকর পে-লোড পাঠাতে পারে (যেমন: ঋণাত্মক মূল্য `price: -500`, বা অবৈধ অ্যাডমিন ফ্ল্যাগ `is_admin: true`)।
- **প্রতিরোধ (Mitigation):** ক্লায়েন্ট-সাইড ভ্যালিডেশন কেবল ইউজার এক্সপেরিয়েন্সের জন্য; সার্ভার-সাইডে প্রতিটি ইনপুট, স্কিমা, অথেনটিকেশন এবং অথরাইজেশন পুনর্মূল্যায়ন করা বাধ্যতামূলক।

### 6. Senior / Staff Engineer Interview Defense

> **ইন্টারভিউয়ার:** *"ক্লায়েন্ট-সার্ভার অ্যাপ্লিকেশনে ক্লায়েন্ট কোড (যেমন মোবাইল অ্যাপ) সবসময় আমাদের নিয়ন্ত্রণের বাইরে থাকে। নতুন ব্যাকএন্ড ফিচার বা ব্রেকিং এপিআই পরিবর্তনের সময় আপনি ক্লায়েন্ট ব্যাকওয়ার্ড কম্প্যাটিবিলিটি কীভাবে পরিচালনা করবেন?"*
>
> 💡 **Staff-Level উত্তরের কাঠামো:**
> "মোবাইল অ্যাপ বা থার্ড-পার্টি ক্লায়েন্টরা ওয়েব ব্রাউজারের মতো সাথে সাথে রিফ্রেশ হয় না; ব্যবহারকারীরা মাসের পর মাস বা বছর ধরে পুরোনো অ্যাপ ভার্সন ব্যবহার করতে পারেন। তাই আমাদের আর্কিটেকচারাল কৌশল হবে:
> 1. **কঠোর API Versioning:** এপিআই রুটে স্পষ্ট ভার্সনিং থাকবে (যেমন `/api/v1/checkout` এবং `/api/v2/checkout`)। v1 কোনো অবস্থাতেই ব্রেক করা যাবে না।
> 2. **Tolerant Reader & Additive Changes:** ব্যাকএন্ড রেসপন্সে কখনো বিদ্যমান ফিল্ড ডিলিট বা রিনেম করা যাবে না; কেবল নতুন অপশনাল ফিল্ড যোগ (Additive change) করতে হবে। প্রোটোকল বাফারের মতো ফরম্যাটে ট্যাগ নম্বর অপরিবর্তিত রাখা হবে।
> 3. **Force-Update & Deprecation Mechanism:** প্রতিটি মোবাইল অ্যাপের স্টার্টআপে একটি রিমোট কনফিগ কল থাকবে যা মিনিমাম সাপোর্টেড ভার্সন চেক করবে। পুরোনো ভার্সনকে সফট-ওয়ার্নিং এবং একটি নির্ধারিত ডেডলাইনের পর হার্ড-ব্লক (Force Update dialog) দিয়ে অ্যাপ স্টোরে রিডাইরেক্ট করা হবে।"

## 📝 Practice Questions

```markdown
### Basic Practice Questions
1. Client-Server আর্কিটেকচারের মূল সংজ্ঞা এবং দুটি প্রধান সত্ত্বার ভূমিকা কী?
2. 2-Tier আর্কিটেকচারের চেয়ে 3-Tier আর্কিটেকচার কেন বেশি সুরক্ষিত এবং স্কেলেবল?
3. Thin Client এবং Thick Client-এর মধ্যকার পার্থক্য কী?
4. "Never Trust the Client" নীতিটি ব্যাকএন্ড সিকিউরিটিতে কেন এত গুরুত্বপূর্ণ?
5. Peer-to-Peer (P2P) আর্কিটেকচারের সাথে Client-Server-এর মূল পার্থক্য কী?

### Intermediate Practice Questions
6. মোবাইল ক্লায়েন্টদের জন্য এপিআই ভার্সনিং (URL path vs Header vs Query param) কীভাবে পরিচালনা করবেন?
7. Client-Server কমিউনিকেশনে Request-Response মডেলের সীমাবদ্ধতা দূর করতে WebSockets এবং Server-Sent Events (SSE) কখন ব্যবহৃত হয়?
8. Backend-for-Frontend (BFF) প্যাটার্ন কীভাবে মোবাইল এবং ওয়েব ক্লায়েন্টের জন্য আলাদা এপিআই প্রয়োজনীয়তা সমাধান করে?
9. ক্লায়েন্ট অ্যাপে অফলাইন ডেটা সিঙ্ক্রোনাইজেশন (Offline-first architecture) কীভাবে ডিজাইন করবেন?
10. ক্লায়েন্ট সাইড স্পুফিং রোধে কীভাবে ক্রিপ্টোগ্রাফিক রিকোয়েস্ট সাইনিং (HMAC) প্রয়োগ করা যায়?

### Advanced / Staff-Level Questions
11. কোটি কোটি মোবাইল ক্লায়েন্টের ট্রাফিক হ্যান্ডেল করার সময় মোবাইল নেটওয়ার্কের ফ্রিকোয়েন্ট ডিসকানেকশন ও আইপি চেঞ্জ হ্যান্ডেল করতে QUIC / HTTP/3 কীভাবে সেশন রেজাম্পশন সমাধান করে?
12. মাইক্রোসার্ভিস ব্যাকএন্ডের সামনে GraphQL বনাম REST ব্যবহার করার সময় ক্লায়েন্ট-ড্রিভেন কোয়েরির পারফরম্যান্স ও সিকিউরিটি ট্রেড-অফ (N+1 problem, Query Depth attack) কীভাবে প্রতিরোধ করবেন?
13. ক্লায়েন্ট ডিভাইসগুলোতে ব্যাটারি খরচ এবং সেলুলার ডেটা ব্যবহার অপ্টিমাইজ করতে পুশ নোটিফিকেশন (FCM/APNS) এবং ব্যাকগ্রাউন্ড ফেচ কীভাবে আর্কিটেক্ট করবেন?
14. রিচ ওয়েব অ্যাপ্লিকেশনে Server-Side Rendering (SSR) বনাম Client-Side Rendering (CSR) বনাম Incremental Static Regeneration (ISR)-এর আর্কিটেকচারাল নির্বাচন কীভাবে করবেন?
15. Client-Server মডেলে ক্লাউড কস্ট কমাতে ক্লায়েন্ট ডিভাইসের কম্পিউটিং পাওয়ার (WebAssembly, Client-side ML inference) ব্যবহারের মাধ্যমে সার্ভার অফলোডিং কীভাবে ডিজাইন করবেন?
```

<summary>👉 <b>Answer Key ও সমাধান দেখতে এখানে ক্লিক করুন</b></summary>

1. **সংজ্ঞা:** ক্লায়েন্ট রিকোয়েস্ট পাঠায় ও ইউআই দেখায়; সার্ভার রিকোয়েস্ট প্রসেস করে, সিকিউরিটি এনফোর্স করে ও ডাটাবেজ এক্সেস দিয়ে রেসপন্স পাঠায়।
2. **3-Tier সুবিধা:** বিজনেস লজিক ক্লায়েন্ট থেকে সরিয়ে আলাদা এপ্লিকেশন সার্ভারে নেওয়ায় ডাটাবেজ ক্রেডেনশিয়াল ক্লায়েন্টের কাছে প্রকাশ পায় না এবং ডেটাবেজ কানেকশন পুলিং করা যায়।
3. **Thin vs Thick:** Thin ক্লায়েন্ট সার্ভার-রেন্ডার্ড ভিউ দেখায়, লোকাল লজিক নেই; Thick ক্লায়েন্ট প্রচুর জাভাস্ক্রিপ্ট/মোবাইল লজিক রান করে এবং শুধু কাঁচা ডেটা সার্ভার থেকে নেয়।
4. **Never Trust Client:** ক্লায়েন্ট-সাইড কোড যেকোনো ব্যবহারকারী ম্যানিপুলেট করতে পারে। তাই সার্ভার-সাইডে পুনরায় ভ্যালিডেশন না করলে সিকিউরিটি ও ব্যবসায়িক ক্ষতি হতে পারে।
5. **P2P vs Client-Server:** P2P-তে কোনো কেন্দ্রীয় সার্ভার নেই, প্রতিটি নোড একই সাথে ক্লায়েন্ট ও সার্ভার হিসেবে কাজ করে সরাসরি ফাইল/মেসেজ শেয়ার করে।
6. **API Versioning:** পাথ ভার্সনিং (`/v1/`) সবচেয়ে স্পষ্ট ও ক্যাশেবল। পুরোনো ভার্সন চালু রেখে নতুন ভার্সনে নতুন ফিল্ড দেওয়া হয়।
7. **WebSockets & SSE:** রিয়েল-টাইম লাইভ আপডেটের জন্য পোলিংয়ের নেটওয়ার্ক ওভারহেড এড়াতে সার্ভার-পুশভিত্তিক সকেট বা ইভেন্ট স্ট্রিম ব্যবহার করা হয়।
8. **BFF Pattern:** মোবাইল অ্যাপের ছোট স্ক্রিনের জন্য অপ্টিমাইজড ছোট পে-লোড এবং ওয়েব অ্যাপের জন্য বিস্তারিত পে-লোড দিতে আলাদা ডেডিকেটেড লাইটওয়েট ব্যাকএন্ড গেটওয়ে রাখা।
9. **Offline-first:** ক্লায়েন্ট লোকাল ডাটাবেজে (SQLite) রাইট করে। নেটওয়ার্ক ফিরলে একটি ব্যাকগ্রাউন্ড সিঙ্ক সার্ভিস ভেক্টর ক্লক বা টাইমস্ট্যাম্প দিয়ে সার্ভারের সাথে কনফ্লিক্ট মার্জ করে।
10. **HMAC Signing:** প্রতিটি রিকোয়েস্টে টাইমস্ট্যাম্প ও পে-লোডের একটি ক্রিপ্টোগ্রাফিক হ্যাশ পাঠানো যা ক্লায়েন্ট ও সার্ভারে থাকা গোপন কি (Secret Key) দিয়ে ভ্যালিডেট হয়, ফলে ম্যান-ইন-দ্য-মিডল পরিবর্তন ধরা পড়ে।
11. **QUIC / HTTP/3:** এটি UDP-ভিত্তিক। কানেকশন আইডি আইপি অ্যাড্রেসের ওপর নির্ভর করে না। ফলে ইউজার ওয়াইফাই থেকে ৪জি মোবাইলে সুইচ করলেও কানেকশন ড্রপ না করে সেশন নিরবচ্ছিন্ন থাকে।
12. **GraphQL Defense:** কুয়েরি ডেপথ লিমিট করা, কুয়েরি কমপ্লেক্সিটি স্কোরিং চালু করা এবং ডাটাবেজ কুয়েরি অপ্টিমাইজ করতে DataLoader দিয়ে ব্যাচিং ও ক্যাশিং নিশ্চিত করা।
13. **Battery Optimization:** অনবরত হার্টবিট পোলিং না করে ওএস লেভেলের সেন্ট্রাল পুশ সার্ভিস (Apple APNs বা Google FCM) ব্যবহার করা, যা ওএস-এর একক রেডিও চ্যানেলে ব্যাটারি সাশ্রয় করে পুশ পাঠায়।
14. **SSR vs CSR vs ISR:** এসইও এবং প্রাথমিক ফার্স্ট-কন্টেন্টফুল-পেইন্টের জন্য SSR; ড্যাশবোর্ড বা ইন্টারনাল পোর্টালের জন্য CSR; কন্টেন্ট সমৃদ্ধ ই-কমার্স পেজের জন্য ISR শ্রেষ্ঠ।
15. **Client-side Offloading:** জটিল ইমেজ প্রসেসিং, ক্লায়েন্ট-সাইড এনক্রিপশন বা টেনসরফ্লো লাইট দিয়ে ফেয়ারনেস ও ভয়েস প্রসেসিং ক্লায়েন্টেই সম্পন্ন করে সার্ভারের সিপিইউ ও ব্যান্ডউইথ খরচ কমানো।
