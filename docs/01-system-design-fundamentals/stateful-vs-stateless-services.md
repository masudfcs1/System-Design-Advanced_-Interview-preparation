## 📖 Deep Dive Notes

### 1. সহজ সংজ্ঞা ও Intuitive Mental Model

একটি সফটওয়্যার সার্ভিসের বিভিন্ন রিকোয়েস্টের মধ্যবর্তী সময়ে ক্লায়েন্টের পূর্ববর্তী তথ্য ও প্রেক্ষাপট (Context/Session/State) সার্ভারের লোকাল মেমোরি বা ডিস্কে ধরে রাখা হচ্ছে কি হচ্ছে না—তার ওপর ভিত্তি করে সার্ভিসকে **Stateless** অথবা **Stateful** শ্রেণীতে বিভক্ত করা হয়।

- **Stateless Service:** সার্ভার তার লোকাল মেমোরিতে কোনো ক্লায়েন্টের পূর্ববর্তী স্টেট ধরে রাখে না। প্রতিটি ইনকামিং রিকোয়েস্ট সম্পূর্ণ স্বয়ংসম্পূর্ণ (Self-contained); অর্থাৎ রিকোয়েস্ট প্রসেস করার সমস্ত তথ্য (যেমন: Auth Token, Payload, Context) ক্লায়েন্ট নিজেই রিকোয়েস্টের সাথে সরবরাহ করে। যেকোনো নোড যেকোনো রিকোয়েস্ট হ্যান্ডেল করতে পারে।
- **Stateful Service:** সার্ভার তার নিজস্ব মেমোরি বা লোকাল স্টোরেজে ক্লায়েন্টের সাথে চলমান কানেকশনের স্টেট, সেশন বা ডেটা বজায় রাখে। পরবর্তী রিকোয়েস্টগুলো সফলভাবে সম্পন্ন হতে পূর্ববর্তী রিকোয়েস্টের তথ্যের ওপর নির্ভর করে।

> 🧠 **Intuitive Mental Model (ফাস্টফুড ক্যাশিয়ার বনাম ব্যক্তিগত চিকিৎসক):**
> - **Stateless (ম্যাকডোনাল্ডস ক্যাশিয়ার):** আপনি ম্যাকডোনাল্ডসের কাউন্টারে গিয়ে বললেন "১টি বার্গার দিন"। তিনি স্লিপ ও বার্গার দিয়ে লেনদেন শেষ করলেন। ১০ মিনিট পর আপনি আবার কাউন্টারে গিয়ে বললেন "১টি কোক দিন"। এবার ভিন্ন ক্যাশিয়ার থাকলেও কোনো সমস্যা নেই, কারণ আপনি নতুন করে অর্ডার দিচ্ছেন এবং দাম পরিশোধ করছেন। আগের অর্ডারের কোনো স্মৃতি এই ক্যাশিয়ারের মেমোরিতে রাখার দরকার নেই।
> - **Stateful (ব্যক্তিগত সাইকিয়াট্রিস্ট / থেরাপিস্ট):** আপনি থেরাপিস্টের সাথে ৩ মাস ধরে সেশন নিচ্ছেন। হঠাৎ মাঝপথে অন্য কোনো নতুন থেরাপিস্ট আপনার সামনে বসিয়ে দিলে সে কিছুই বুঝবে না, কারণ আপনার সমস্ত আবেগ, পূর্ববর্তী হিস্ট্রি ও প্রেক্ষাপট আগের ডাক্তারের ব্রেইনে স্টোর করা আছে (**Stateful Connection**)!

### 2. Stateless Architecture: স্কেলিংয়ের স্বর্ণযুগ

আধুনিক ক্লাউড-নেটিভ মাইক্রোসার্ভিস (Kubernetes, AWS ECS, Serverless Lambda) মূলত স্ট্যাটলেস আর্কিটেকচারের ওপর ভিত্তি করে গড়ে উঠেছে।

```
Stateless Architecture:
                       [ Load Balancer (Round Robin) ]
                                      │
            ┌─────────────────────────┼─────────────────────────┐
            ▼                         ▼                         ▼
      [ App Node 1 ]            [ App Node 2 ]            [ App Node 3 ]
      (No Local State)          (No Local State)          (No Local State)
            │                         │                         │
            └─────────────────────────┼─────────────────────────┘
                                      ▼
             [ Shared State Store: Redis Cluster / Database ]
```

#### সেশন হ্যান্ডলিং কৌশল:
1. **Client-side State (JWT - JSON Web Tokens):** ব্যবহারকারীর আইডি ও রোল ক্রিপ্টোগ্রাফিকভাবে সাইন করে ক্লায়েন্টের ব্রাউজার বা অ্যাপে পাঠিয়ে দেওয়া হয়। সার্ভারের কোনো ডাটাবেজ লুকআপও লাগে না।
2. **External Shared Cache (Redis / Memcached):** ক্লায়েন্টকে একটি সেশন আইডি (UUID) কুকি দেওয়া হয়। সার্ভার নোডগুলো সেন্ট্রাল Redis ক্লাস্টার থেকে সেশন রিড করে। নোড ক্র্যাশ করলেও সেশন নষ্ট হয় না।

---

### 3. Stateful Architecture: কখন এবং কেন অপরিহার্য?

সবকিছু স্ট্যাটলেস করা সম্ভব নয়। নিচের ক্ষেত্রগুলোতে স্টেটফুল সার্ভিস বাধ্যতামূলক:
1. **Real-time WebSockets (Live Chat, Stock Tickers):** ক্লায়েন্ট এবং সার্ভারের মধ্যে একটি দীর্ঘস্থায়ী TCP সকেট কানেকশন ওপেন থাকে। মেমোরিতে সরাসরি কানেকশন অবজেক্ট থাকে।
2. **Multiplayer Gaming Engines:** প্রতিটি খেলোয়াড়ের রিয়েল-টাইম অবস্থান ($x, y, z$ coordinates) প্রতি সেকেন্ডে ৬০ বার আপডেট হয়, যা ডাটাবেজে না লিখে সার্ভার র‍্যামে ধরে রাখতে হয়।
3. **In-Memory Caches & Databases (Redis, Kafka Brokers, Cassandra):** ডেটা সরাসরি মেমোরি ও ডিস্কে সাজিয়ে রাখা হয়।

```
Stateful Architecture (Sticky Session / Consistent Hashing):
[ Client A ] ──────────────────────────┐
                                       ▼
                             [ Load Balancer ]
                             (Hash Ring / Sticky)
                               ┌───────┴───────┐
                               ▼               ▼
                       [ Server Node 1 ] [ Server Node 2 ]
                        (Holds Socket A)  (Holds Socket B)
```

### 4. Alternatives & Trade-offs Comparison Matrix

| বৈশিষ্ট্য | Stateless Service | Stateful Service |
|---|---|---|
| **হরাইজন্টাল স্কেলিং** | তাৎক্ষণিক ও অত্যন্ত সহজ (Auto-scale up/down) | জটিল (ডেটা রি-পার্টিশন ও কানেকশন হ্যান্ডেলিং প্রয়োজন) |
| **নোড ক্র্যাশ ও ফেইলিউর** | জিরো ইমপ্যাক্ট (লোড ব্যালেন্সার ট্রাফিক অন্য নোডে পাঠায়) | কানেকশন ড্রপ হয়; স্টেট রিকভারি করতে হয় |
| **লোড ব্যালেন্সিং অ্যালগরিদম** | সাধারণ Round Robin, Least Connections | IP Hash, Sticky Session, Consistent Hashing |
| **পারফরম্যান্স ও ল্যাটেন্সি** | শেয়ার্ড স্টোর বা ডিবিতে নেটওয়ার্ক কলের ল্যাটেন্সি (+২-১০ms) | লোকাল র‍্যাম এক্সেসের কারণে অতি দ্রুত (মাইক্রোসেকেন্ড) |
| **ডিপ্লয়মেন্ট রোলআউট** | ব্লু-গ্রিন বা রোলিং আপডেট অত্যন্ত সহজ | কানেকশন ড্রেনিং (Connection Draining) বাধ্যতামূলক |

### 5. Failure Modes & Production Mitigations

#### Failure Mode 1: Node Termination during Live WebSocket Connections
- **ঝুঁকি:** কুবারনেটিস অটো-স্কেলিং একটি স্টেটফুল পড ডিলিট করার সাথে সাথে লাখ লাখ লাইভ চ্যাট কানেকশন এক সেকেন্ডে ড্রপ করে, যা ক্লায়েন্টদের পক্ষ থেকে রিট্রাই স্টর্ম তৈরি করে।
- **প্রতিরোধ (Mitigation):** **Graceful Shutdown & Connection Draining:** পড টার্মিনেট করার সংকেত (SIGTERM) পেলে নতুন কানেকশন বন্ধ করা এবং ধাপে ধাপে জিটার সহকারে কয়েক মিনিটের মধ্যে বিদ্যমান কানেকশনগুলো অন্য নোডে রি-কানেক্ট হতে বলা।

#### Failure Mode 2: Hotspot Node in Sticky Sessions
- **ঝুঁকি:** লোড ব্যালেন্সারে আইপি স্টিকিনেস থাকলে একটি বড় কর্পোরেট অফিসের হাজার হাজার কর্মী একটি সিঙ্গেল ন্যাটেড (NAT) আইপি দিয়ে এসে একটি মাত্র নোডে লোড ফেলে সেটিকে ক্র্যাশ করায়।
- **প্রতিরোধ:** আইপি বেসড স্টিকিনেস বাদ দিয়ে ক্রিপ্টোগ্রাফিক সেশন কুকি বেসড অ্যাফিনিটি রাউটিং ব্যবহার করা।

### 6. Senior / Staff Engineer Interview Defense

> **ইন্টারভিউয়ার:** *"আমরা একটি রিয়েল-টাইম কোলাবোরেটিভ ডকুমেন্ট এডিটর (যেমন Google Docs বা Figma) ডিজাইন করছি। আপনি কি আর্কিটেকচারটি Stateless করবেন নাকি Stateful?"*
>
> 💡 **Staff-Level উত্তরের কাঠামো:**
> "Google Docs বা Figma-এর মতো অ্যাপ্লিকেশনে কোটি কোটি এডিটিং অপারেশন সাব-মিলিসেকেন্ড ল্যাটেন্সিতে হ্যান্ডেল করতে হয়।
> 1. **কোর এডিটিং ইঞ্জিন (Stateful Architecture):** আমরা ডকুমেন্ট এডিটিং সেশনের জন্য **Stateful WebSocket Cluster** ব্যবহার করব। প্রতিটি ডকুমেন্টের মেমোরি স্টেট একটি নির্দিষ্ট নোডের র‍্যামে অপারেশনাল ট্রান্সফর্মেশন (OT) বা CRDT ডেটা স্ট্রাকচার হিসেবে লোড থাকবে। কনসিস্টেন্ট হ্যাশিং দিয়ে ডকুমেন্ট আইডির ভিত্তিতে একই ডকুমেন্টের সমস্ত ব্যবহারকারীকে একই নোডে রাউট করব, যা তাৎক্ষণিক মেমোরি কনফ্লিক্ট মার্জিং নিশ্চিত করবে।
> 2. **রেজিলিয়েন্স ও ডুরাবিলিটি:** মেমোরি স্টেট লসের হাত থেকে বাঁচতে ব্যাকগ্রাউন্ডে সমস্ত অপারেশন Kafka বা Redis Append-Only লগে স্ট্রিম হবে এবং প্রতি ৩০ সেকেন্ডে স্ন্যাপশট S3/ডাটাবেজে পারসিস্ট হবে।
> 3. **বাকি অ্যাপ্লিকেশন (Stateless Architecture):** ব্যবহারকারীর অথেনটিকেশন, ফাইল ব্রাউজিং, বিলিং এবং পারমিশন ম্যানেজমেন্ট সম্পূর্ণ স্ট্যাটলেস সার্ভিস হিসেবে চলবে।"

2. Stateless সার্ভিসে ব্যবহারকারীর লগইন সেশন সাধারণত কীভাবে হ্যান্ডেল করা হয়?

10. আইপি-বেসড স্টিকি সেশন ব্যবহারের সবচেয়ে বড় ড্র-ব্যাক কী?

## 🔑 Answer Key & Self-Test Evaluation

<details>
<summary>👉 <b>Answer Key ও সমাধান দেখতে এখানে ক্লিক করুন</b></summary>

1. **পার্থক্য:** Stateless লোকাল মেমোরিতে কোনো স্টেট রাখে না, প্রতি রিকোয়েস্ট স্বাধীন; Stateful পূর্ববর্তী রিকোয়েস্টের কনটেক্সট বা দীর্ঘস্থায়ী সকেট মেমোরিতে ধরে রাখে।
2. **Stateless Session:** ক্লায়েন্ট-সাইড সাইনড JWT টোকেন অথবা শেয়ার্ড সেন্ট্রালাইজড ইন-মেমোরি স্টোর (যেমন Redis Cluster)-এ সেশন কি সংরক্ষণ করে।
3. **Sticky Session:** লোড ব্যালেন্সারের একটি বৈশিষ্ট্য যা নিশ্চিত করে একজন নির্দিষ্ট ইউজারের পরবর্তী সমস্ত রিকোয়েস্ট সবসময় ক্লাস্টারের একই নির্দিষ্ট ব্যাকএন্ড সার্ভারে রাউট হবে।
4. **গেমে কেন স্টেটফুল:** গেমে প্রতি সেকেন্ডে শত শত ইনপুট থাকে। প্রতি রিকোয়েস্টে ডাটাবেজ বা রেডিস হিট করলে ল্যাটেন্সি বেড়ে গেম আনপ্লেয়েবল হয়ে যাবে; র‍্যামে মেমোরি স্টেট রাখা বাধ্যতামূলক।
5. **নোড ক্র্যাশ প্রভাব:** স্ট্যাটলেসে কোনো প্রভাব পড়ে না; লোড ব্যালেন্সার ট্রাফিক অন্য নোডে ঘুরিয়ে দেয় এবং ইউজার লগড-ইন থাকে।
6. **JWT সুবিধা ও ঝুঁকি:** সুবিধা: ডাটাবেজ লুকআপ লাগে না; ঝুঁকি: টোকেন লিক হলে বা ইউজার ব্যান করলে মেয়াদ শেষ না হওয়া পর্যন্ত সার্ভার থেকে সহজে রিভোক করা যায় না (ব্ল্যাকলিস্ট রেডিসে রাখতে হলে স্ট্যাটলেস সুবিধা নষ্ট হয়)।
7. **WebSocket + Redis Pub/Sub:** ইউজার A নোড ১-এ কানেক্টেড এবং ইউজার B নোড ২-এ কানেক্টেড। নোড ১ মেসেজটি Redis চ্যানেলে পাবলিশ করে। নোড ২ সাবস্ক্রাইব করে মেসেজটি গ্রহণ করে ইউজার B-এর সকেটে পুশ করে।
8. **Connection Draining:** সার্ভার রিস্টার্ট বা শাটডাউনের সময় নতুন ট্রাফিক না নিয়ে চলমান সকেট বা রিকোয়েস্টগুলো শেষ করার জন্য নির্দিষ্ট সময় অপেক্ষা করা, যাতে ইউজার ডিসকানেক্ট না হয়।
9. **Consistent Hashing:** সেশন বা চ্যানেল আইডির হ্যাশ মান একটি রিংয়ে স্থাপন করা। একটি নোড মরলে কেবল সেই নোডের কানেকশন রি-রাউট হয়, বাকি ক্লাস্টারের কানেকশন অক্ষুণ্ণ থাকে।
10. **IP Sticky ড্রব্যাক:** একই কর্পোরেট নেটওয়ার্ক বা মোবাইল টাওয়ারের শত শত ইউজার একটি পাবলিক NAT আইপি শেয়ার করে, ফলে একটি নির্দিষ্ট সার্ভারে অস্বাভাবিক ট্রাফিক ঢুকে হটস্পট তৈরি করে।
11. **Collaborative Docs:** মেমোরিতে CRDT স্টেট রাখা, WebSocket দিয়ে রিয়েল-টাইম অপারেশন ব্রডকাস্ট করা, এবং ইমিউটেবল অপারেশনের লগ Kafka-তে লিখে ডিস্কে ডুরাবিলিটি নিশ্চিত করা।
12. **StatefulSet vs Deployment:** StatefulSet প্রতিটি পডকে একটি ইউনিক প্রেডিক্টেবল নেটওয়ার্ক আইডি (`pod-0`, `pod-1`) এবং ডেডিকেটেড পারসিস্টেন্ট ভলিউম দেয় যা রিস্টার্টেও বদলায় না। Deployment সম্পূর্ণ রিপ্লেসেবল এবং স্ট্যাটলেস।
13. **Unplanned Node Crash State:** Write-Ahead Logging (WAL) বা রিয়েল-টাইম ইন-মেমোরি রেপ্লিকেশন (Active-Passive Buddy Node) ব্যবহার করা, যাতে ক্র্যাশের সাথে সাথে বাডি নোড মেমোরি স্টেট টেকওভার করতে পারে।
14. **Lambda RDS Proxy:** প্রতিটি ল্যাম্বডা নতুন কানেকশন খুলে ডাটাবেজ কানেকশন লিমিট শেষ করে ফেলে। RDS Proxy মাঝে বসে কানেকশন পুল ধরে রাখে এবং ল্যাম্বডাকে দ্রুত কানেকশন শেয়ার করতে দেয়।
15. **1M WebSockets:** লিনাক্স `epoll`/kqueue ইভেন্ট লুপ ব্যবহার করা, থ্রেড-প্রতি-কানেকশন মডেল বাদ দিয়ে নন-ব্লকিং I/O বা গো-রুটিন ব্যবহার করা এবং OS কার্নেল টিউনিং (`sysctl` max file descriptors ও TCP বাফার সাইজ কমিয়ে র‍্যাম বাঁচানো)।
