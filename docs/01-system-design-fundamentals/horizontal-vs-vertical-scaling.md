# Horizontal vs Vertical Scaling

[Back to System Design Fundamentals topics](README.md) · [Module guide](../01-system-design-fundamentals.md)

## 📌 Learning Checklist
- [ ] Clearly contrast Scale-Up (Vertical) vs Scale-Out (Horizontal).
- [ ] Identify physical limits, hardware bottlenecks, and diminishing returns of Vertical Scaling.
- [ ] Understand architectural challenges of Horizontal Scaling (Statelessness, Distributed Consensus, Database Sharding).
- [ ] Analyze financial economics and cost curves (Commodity hardware vs Mega-servers).
- [ ] Learn when Vertical Scaling is the smarter first move before rushing into Horizontal Scaling.
- [ ] Defend hybrid scaling architectures in Staff-level interviews.

## 📖 Deep Dive Notes

### 1. সহজ সংজ্ঞা ও Intuitive Mental Model

সিস্টেমের ব্যবহারকারী বা ট্রাফিক যখন ক্রমাগত বাড়তে থাকে, তখন সেই বর্ধিত লোড নিরাপদে হ্যান্ডেল করার জন্য কম্পিউটিং রিসোর্স বাড়ানোর দুটি প্রধান পথ হলো **Vertical Scaling** এবং **Horizontal Scaling**।

```
[ Vertical Scaling (Scale Up) ]            [ Horizontal Scaling (Scale Out) ]
      ┌──────────────┐                       ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐
      │  64 vCPU     │                       │ 2vCPU│ │ 2vCPU│ │ 2vCPU│ │ 2vCPU│
      │  256 GB RAM  │                       │ 8GB  │ │ 8GB  │ │ 8GB  │ │ 8GB  │
      │  4 TB NVMe   │                       └──────┘ └──────┘ └──────┘ └──────┘
      └──────────────┘                       (Load Balancer distributes traffic)
(একক শক্তিশালী সুপার সার্ভার)                  (একাধিক সাধারণ কমোডিটি সার্ভারের ক্লাস্টার)
```

> 🧠 **Intuitive Mental Model (ভারী মাল পরিবহন অ্যানালজি):**
> ধরা যাক একটি ফ্যাক্টরিতে পণ্য পরিবহনের জন্য মালবাহী ভ্যান দরকার।
> - **Vertical Scaling (Scale Up):** আপনার ছোট পিকআপ ভ্যানটি বিক্রি করে একটি বিশাল ২০ চাকার দানবাকৃতির মেগা-ট্রাক কিনে নিলেন। এটি আগের চেয়ে ১০ গুণ বেশি মাল একবারে নিতে পারে। কিন্তু সমস্যা হলো—রাস্তার ব্রিজ বা টানেলের উচ্চতার কারণে মেগা-ট্রাকের চেয়ে বড় আর কোনো ট্রাক পৃথিবীতে বানানো সম্ভব নয় (**Hardware Limit**), এবং ওই একক ট্রাকটি নষ্ট হলে পুরো ফ্যাক্টরির পরিবহন বন্ধ (**Single Point of Failure**)!
> - **Horizontal Scaling (Scale Out):** একটি মেগা-ট্রাক না কিনে আপনি ১০টি সাধারণ সাশ্রয়ী পিকআপ ভ্যানের একটি ফ্লিট তৈরি করলেন। একটি ভ্যান নষ্ট হলে বাকি ৯টি ভ্যান কাজ চালিয়ে নেবে (**Fault Tolerant**)। ফ্যাক্টরি আরও বড় হলে কালকেই আরও ৫টি ভ্যান বহরে যুক্ত করতে পারবেন (**Elastic Scaling**)।

### 2. Vertical Scaling: সুবিধা, সীমাবদ্ধতা ও আর্থিক বাস্তবতা

#### সুবিধা:
1. **জিরো আর্কিটেকচারাল জটিলতা:** সফটওয়্যার কোডবেস বা সিস্টেমে কোনো পরিবর্তন করার প্রয়োজন নেই। মোনোলিথিক অ্যাপ্লিকেশনটি যেমন আছে তেমনই থাকবে।
2. **জিরো নেটওয়ার্ক ওভারহেড:** মেমোরিতে সরাসরি ইন্টার-প্রসেস কমিউনিকেশন (IPC) চলে, কোনো ডিস্ট্রিবিউটেড নেটওয়ার্ক সিরিয়ালাইজেশন বা RPC ল্যাটেন্সি নেই।
3. **সহজ ACID ট্রানজ্যাকশন:** একক আরডিবিএমএস ডাটাবেজে লক ও ট্রানজ্যাকশন স্বাভাবিকভাবেই পারফেক্ট কাজ করে।

#### সীমাবদ্ধতা ও চরম সত্য:
1. **হার্ডওয়্যার লিমিট (Ceiling):** পৃথিবীর সবচেয়ে বড় AWS EC2 ইনস্ট্যান্সের (যেমন `u-24tb1.112xlarge`) সর্বোচ্চ সীমা হলো ২৪ টেরাবাইট র‍্যাম এবং ৪৪৮টি ভার্চুয়াল কোর। আপনার ডেটা বা লোড এর চেয়ে বেশি হলে আপনি চাইলেও আর কোনো বড় সার্ভার পাবেন না।
2. **এক্সপোনেনশিয়াল কস্ট কার্ভ (Exponential Cost):** একটি সাধারণ ১৬ জিবি র‍্যামের সার্ভারের চেয়ে ১২৮ জিবি সার্ভারের দাম ৮ গুণ হতে পারে, কিন্তু ২ টেরাবাইট র‍্যামের সার্ভারের দাম সাধারণ সার্ভারের চেয়ে ১০০ গুণ বেশি হয়!
3. **ডাউনটাইম রিকোয়ারমেন্ট:** সিপিইউ বা র‍্যাম আপগ্রেড করতে সাধারণত সার্ভার রিস্টার্ট দিতে হয়, ফলে পরিকল্পিত ডাউনটাইম (Maintenance Downtime) লাগে।
4. **সিঙ্গেল পয়েন্ট অব ফেইলিউর (SPOF):** সার্ভারের মাদারবোর্ড বা পাওয়ার সাপ্লাই নষ্ট হলে পুরো ব্যবসা স্থবির হয়ে পড়ে।

### 3. Horizontal Scaling: আর্কিটেকচারাল চ্যালেঞ্জসমূহ

হরাইজন্টাল স্কেলিং তাত্ত্বিকভাবে সীমাহীন স্কেলের প্রতিশ্রুতি দিলেও এটি সিস্টেমে বিশাল প্রকৌশলগত জটিলতা নিয়ে আসে:

```
                          [ Internet ]
                               │
                               ▼
                   [ Load Balancer (Nginx/ALB) ]
                               │
            ┌──────────────────┼──────────────────┐
            ▼                  ▼                  ▼
      [ App Server 1 ]   [ App Server 2 ]   [ App Server 3 ]  <-- Stateless Layer
            │                  │                  │
            └──────────────────┼──────────────────┘
                               ▼
               [ Shared Session & Cache (Redis) ]
                               │
                               ▼
          [ Sharded Database / NoSQL Cluster (Cassandra) ]
             [ Shard 1 ]      [ Shard 2 ]      [ Shard 3 ]
```

1. **Stateless Services:** সার্ভারগুলোকে অবশ্যই স্ট্যাটলেস হতে হবে। ইউজারের সেশন লোকাল মেমোরিতে রাখা যাবে না; তা শেয়ার্ড Redis বা টোকেনে (JWT) রাখতে হবে।
2. **Database Sharding & Partitioning:** ডাটাবেজ এক মেশিনে না আঁটলে ডেটাকে বিভিন্ন শার্ডে ভাগ করতে হয় (Consistent Hashing দিয়ে)। এতে ক্রস-শার্ড জয়েন (Cross-shard JOIN) এবং ডিস্ট্রিবিউটেড ট্রানজ্যাকশন অসম্ভব জটিল হয়ে পড়ে।
3. **Network Complexity:** প্রতিটা সার্ভারের মধ্যে যোগাযোগে নেটওয়ার্ক ল্যাটেন্সি, প্যাকেট লস এবং সিকিউরিটি (TLS encryption) ম্যানেজ করতে হয়।

### 4. Alternatives & Trade-offs Comparison Matrix

| প্যারামিটার | Vertical Scaling (Scale Up) | Horizontal Scaling (Scale Out) |
|---|---|---|
| **সর্বোচ্চ ক্ষমতা** | ফিজিক্যাল মেশিনের সর্বোচ্চ ক্যাপাসিটিতে সীমাবদ্ধ | তাত্ত্বিকভাবে সীমাহীন (হাজার হাজার নোড) |
| **ফল্ট টলারেন্স** | শূন্য (SPOF - সার্ভার ডাউন মানে সব ডাউন) | চমৎকার (যেকোনো নোড ড্রপ করলে ট্রাফিক অন্য নোডে যায়) |
| **ডিপ্লয়মেন্ট ও অটো-স্কেলিং** | তাৎক্ষণিক স্কেলিং সম্ভব নয় (রিস্টার্ট লাগে) | ট্রাফিক স্পাইকে মিনিটের মধ্যে অটো-স্কেলিং গ্রুপে নোড অ্যাড/রিমুভ |
| **কোড ও আর্কিটেকচার** | কোনো পরিবর্তন লাগে না | স্ট্যাটলেস ডিজাইন, ডিস্ট্রিবিউটেড ক্যাশ ও শার্ডিং বাধ্যতামূলক |
| **খরচ কাঠামো** | শুরুতে সস্তা কিন্তু হাই-এন্ডে অতি ব্যয়বহুল | লিনিয়ার কস্ট কার্ভ (কমদামী কমোডিটি সার্ভার ব্যবহার) |

### 5. Failure Modes & Production Mitigations

#### Failure Mode 1: Premature Horizontal Scaling (অকাল মাইক্রোসার্ভিস ও শার্ডিং)
- **ঝুঁকি:** স্টার্টআপ অবস্থায় মাত্র ১০ হাজার ইউজারের জন্য হরাইজন্টাল শার্ডিং ও মাইক্রোসার্ভিস করতে গিয়ে টিম নেটওয়ার্ক বাগ, কনসিস্টেন্সি জটিলতা ও অপারেশনের চাপে ধসে পড়ে।
- **প্রতিরোধ (Mitigation):** আধুনিক একটি শক্তিশালী $300/month ক্লাউড সার্ভারেই লক্ষাধিক ট্রাফিক হ্যান্ডেল করা সম্ভব। প্রথমে আর্কিটেকচার অপ্টিমাইজ এবং ভার্টিক্যাল স্কেলিং করা বুদ্ধিমানের কাজ।

#### Failure Mode 2: Hotspot Sharding in Horizontal Scaling
- **ঝুঁকি:** ইউজারদের আইডি দিয়ে সমানভাবে শার্ড করা সত্ত্বেও কোনো সেলিব্রিটি ইউজারের শার্ডে অতিরিক্ত ৯৯% ট্রাফিক ঢুকে সেই নির্দিষ্ট হরাইজন্টাল নোডটি ক্র্যাশ করে।
- **প্রতিরোধ:** Salting Key, Consistent Hashing এবং সেলিব্রিটি ডেটার জন্য আলাদা ইন-মেমোরি ক্যাশিং লেয়ার।

### 6. Senior / Staff Engineer Interview Defense

> **ইন্টারভিউয়ার:** *"আমাদের সিস্টেমে ট্রাফিক দ্বিগুণ হতে চলেছে। আমরা কি আরও সার্ভার কিনে হরাইজন্টালি স্কেল করব?"*
>
> 💡 **Staff-Level উত্তরের কাঠামো:**
> "ট্রাফিক দ্বিগুণ হওয়া মানেই চোখ বন্ধ করে নতুন সার্ভার যোগ করা সঠিক সিনিয়র ইঞ্জিনিয়ারিং অ্যাপ্রোচ নয়:
> 1. **প্রথম ধাপ - প্রোফাইলিং ও বটলনেক বিশ্লেষণ:** আমাদের বর্তমান সার্ভারের CPU, মেমোরি এবং ডাটাবেজ I/O বিশ্লেষণ করতে হবে। ডাটাবেজে একটি মিসিং ইনডেক্স যোগ করলে বা স্লো কুয়েরি অপ্টিমাইজ করলে অনেক সময় বর্তমান মেশিনের ক্যাপাসিটিই ৫ থেকে ১০ গুণ বৃদ্ধি পায়।
> 2. **অ্যাপ্লিকেশন টায়ার (Stateless):** অ্যাপ্লিকেশন লেয়ারে আমরা অবিলম্বে হরাইজন্টাল স্কেলিং ও অটো-স্কেলিং গ্রুপ ব্যবহার করব, কারণ স্ট্যাটলেস সার্ভার বাড়ানো সাশ্রয়ী এবং নো-ঝুঁকি।
> 3. **ডাটাবেজ টায়ার (Stateful):** ডাটাবেজ লেয়ারে শার্ডিং একটি অত্যন্ত ব্যয়বহুল ও ঝুঁকিপূর্ণ স্থাপত্যিক সিদ্ধান্ত। তাই ডাটাবেজের ক্ষেত্রে আমরা প্রথমে ভার্টিক্যাল স্কেলিং (RAM বাড়িয়ে সম্পূর্ণ ওয়ার্কিং সেট ক্যাশ করা) এবং রিড ট্রাফিকের জন্য Read-Replicas যোগ করব। কেবল যখন একক নোডের ডিস্ক I/O বা রাইট ট্রাফিক চরম সীমাতে পৌঁছাবে, তখনই আমরা হরাইজন্টাল শার্ডিং বা ডিস্ট্রিবিউটেড ডাটাবেজে (যেমন CockroachDB/Cassandra) মাইগ্রেট করব।"

10. অ্যামাহডলস ল (Amdahl's Law) কীভাবে প্রমাণ করে যে সমান্তরাল প্রসেসর বা নোড যোগ করলেও একটি নির্দিষ্ট সীমার পর পারফরম্যান্স আর বাড়ে না?

## 🔑 Answer Key & Self-Test Evaluation

<details>
<summary>👉 <b>Answer Key ও সমাধান দেখতে এখানে ক্লিক করুন</b></summary>

1. **মৌলিক সংজ্ঞা:** Vertical Scaling মানে একক মেশিনের শক্তি বাড়ানো (CPU/RAM); Horizontal Scaling মানে সমান্তরাল নোডের সংখ্যা বাড়ানো।
2. **Commodity Hardware:** সাধারণ, সুলভ ও প্রমিত হার্ডওয়্যার স্পেসিফিকেশনের মেশিন, যা দামি সুপার সার্ভারের বিকল্প হিসেবে ক্লাস্টারে ব্যবহার করা হয়।
3. **Stateless প্রয়োজন কেন:** ট্রাফিক যেকোনো মুহূর্তে যেকোনো সার্ভার নোডে যেতে পারে। যদি একটি সার্ভারের মেমোরিতে ইউজারের লগইন ডেটা থাকে এবং পরের রিকোয়েস্ট অন্য সার্ভারে যায়, তবে ইউজার লগআউট হয়ে যাবে।
4. **অটো-স্কেলিং সঙ্গতি:** Horizontal Scaling-এর সাথে, কারণ ট্রাফিকের ওঠানামার সাথে সাথে ক্লাউডে নতুন VM বা কন্টেইনার দ্রুত স্পিন-আপ বা শাটডাউন করা যায়।
5. **ভার্টিক্যাল সীমাবদ্ধতা:** ১) হার্ডওয়্যারের সর্বোচ্চ সীমা আছে, ২) একক পয়েন্ট অফ ফেইলিউর (SPOF)।
6. **সেশন ও ফাইল ডিস্ট্রিবিউশন:** লোকাল ড্রাইভের বদলে ফাইল স্টোরেজ হিসেবে S3/GCS এবং ইন-মেমোরি সেশনের বদলে সেন্ট্রালাইজড Redis ক্লাস্টার ব্যবহার করা।
7. **Read-Replicas vs Sharding:** যদি ট্রাফিকের সিংহভাগ রিড কুয়েরি হয় ($>90\%$), তবে রিড-রেপ্লিকা যথেষ্ট। কিন্তু যদি রাইট ট্রাফিক এবং ডেটাবেজ সাইজ একক মেশিনের স্টোরেজ ও I/O লিমিট ছাড়িয়ে যায়, তখন শার্ডিং প্রয়োজন।
8. **Scale-Up First নীতি:** ডিস্ট্রিবিউটেড সিস্টেমের জটিলতা (নেটওয়ার্ক পার্টিশন, কনসিস্টেন্সি লস, ডিফেক্ট ট্র্যাকিং) এড়িয়ে একটি শক্তিশালী একক নোড দিয়ে কম খরচে দ্রুত বিজনেস ভ্যালিডেশন সম্ভব।
9. **Consistent Hashing:** হ্যাশ রিং ব্যবহার করার ফলে একটি নতুন নোড যুক্ত বা বাদ দিলে শুধুমাত্র তার নিকটবর্তী প্রতিবেশীর ডেটা রি-ডিস্ট্রিবিউট হয়, পুরো ক্লাস্টারের সমস্ত ডেটা সরাতে হয় না ($K/N$ ডেটা মুভ হয়)।
10. **Amdahl's Law:** প্রোগ্রামের যে অংশটি সমান্তরাল করা যায় না (Serial portion), সমান্তরাল নোড সংখ্যা যতই বাড়ানো হোক না কেন, সিস্টেমের স্পিড-আপ সেই সিরিয়াল অংশের সীমার দ্বারা অবরুদ্ধ থাকে।
11. **Cross-shard 2PC এড়ানো:** ডেটাকে এমন একটি স্বাভাবিক পার্টিশন কি (যেমন `tenant_id` বা `user_id`) দিয়ে শার্ড করা যাতে সংশ্লিষ্ট সমস্ত রেকর্ড একই শার্ডে অবস্থান করে। ফলে সমস্ত ট্রানজ্যাকশন সিঙ্গেল-শার্ড লোকাল ট্রানজ্যাকশনে পরিণত হয়।
12. **Custom HPA Scaling:** সিপিইউ মেট্রিক্স অনেক সময় ট্রাফিক স্পাইকের পরে বাড়ে (Lagging Indicator)। কাফকা ল্যাগ বা কিউ লেন্থ মেট্রিক্স দেখে রিকোয়েস্ট প্রসেস হওয়ার আগেই কুবারনেটিস দ্রুত পড সংখ্যা বাড়াতে পারে (Leading Indicator)।
13. **Shared-Nothing Architecture:** কোনো সেন্ট্রাল ডিস্ক বা মেমোরি লক শেয়ার না করে প্রতিটি নোড সম্পূর্ণ স্বাধীনভাবে কাজ করে। ফলে কোনো সেন্ট্রাল বাস বা রিসোর্স কনটেনশন ছাড়াই লিনিয়ারলি স্কেল করা যায়।
14. **Cell-based Architecture:** সিস্টেমকে একাধিক স্বাধীন, স্বয়ংসম্পূর্ণ ক্ষুদ্র ক্লাস্টারে (Cell) বিভক্ত করা। একটি সেলে বিভ্রাট বা বাগ দেখা দিলে কেবল ওই সেলের ইউজাররা ক্ষতিগ্রস্ত হয়, বাকি সিস্টেম সম্পূর্ণ সচল থাকে।
15. **Spot & ARM Optimization:** স্ট্যাটলেস ক্লাস্টারে সস্তা স্পট ইনস্ট্যান্স চালানো এবং স্পট ইন্টারাপশন হ্যান্ডলার রাখা; x86 প্রসেসরের বদলে উচ্চ কর্মক্ষম ও সাশ্রয়ী ARM আর্কিটেকচার (যেমন AWS Graviton) গ্রহণ করা।
