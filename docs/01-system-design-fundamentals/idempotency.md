## 📖 Deep Dive Notes

### 1. সহজ সংজ্ঞা ও Intuitive Mental Model

গণিত এবং কম্পিউটার সায়েন্সে **Idempotency** (আইডেমপোটেন্সি) হলো একটি অপারেশনের এমন একটি অনন্য গুণ, যেখানে একই অপারেশন একবার এক্সিকিউট করলে সিস্টেমে যে পরিবর্তন হয়, পরবর্তীতে হুবহু একই ইনপুট দিয়ে যতবারই (শতবার বা হাজারবার) এক্সিকিউট করা হোক না কেন—সিস্টেমের চূড়ান্ত অবস্থা (State) অপরিবর্তিত থাকে এবং কোনো অনিচ্ছাকৃত পার্শ্বপ্রতিক্রিয়া (Side Effect) ঘটে না।

$$\mathbf{f(f(x)) = f(x)}$$

> 🧠 **Intuitive Mental Model (লিফটের বোতাম অ্যানালজি):**
> আপনি একটি বহুতল ভবনের ৫ তলায় যাওয়ার জন্য লিফটের ৫ নম্বর বোতামটি চাপলেন। বোতামটি জ্বলে উঠল।
> অধৈর্য হয়ে আপনি বোতামটি পরপর আরও ১০ বার চাপলেন। লিফট কিন্তু ৫ তলায় ১০ বার যাবে না, একবারই যাবে! 
> বোতামে একবার চাপ দেওয়া আর ১০ বার চাপ দেওয়ার ফলাফল হুবহু এক। এটিই হলো **Idempotent behavior**।
> বিপরীতে, এটিএম বুথে গিয়ে "টাকা উত্তোলন" বাটনে ১০ বার চাপ দিলে যদি ১০ বারই আপনার একাউন্ট থেকে টাকা কেটে বের করে দেয়, তবে সেটি হলো **Non-idempotent disaster**!

### 2. HTTP প্রোটোকল ও মেথডের আইডেমপোটেন্সি

RFC 7231 অনুযায়ী HTTP মেথডসমূহের আইডেমপোটেন্সির মানদণ্ড:

| HTTP Method | Idempotent? | Safe (Read-only)? | ব্যাখ্যা |
|---|:---:|:---:|---|
| **GET** | ✅ হ্যাঁ | ✅ হ্যাঁ | ডাটা রিড করে; সিস্টেমে কোনো স্টেট পরিবর্তন করে না। |
| **PUT** | ✅ হ্যাঁ | ❌ না | রিসোর্সকে নির্দিষ্ট স্টেট দিয়ে রিপ্লেস করে। একই পে-লোড ১০ বার পাঠালেও স্টেট এক থাকে। |
| **DELETE** | ✅ হ্যাঁ | ❌ না | আইডি ডিলিট করে। প্রথমবার ডিলিট হয়ে যায়, পরেরবার রিকোয়েস্টে রিসোর্সটি ইতিমধ্যে অনুপস্থিত থাকে (ফলাফল একই: রিসোর্স নেই)। |
| **POST** | ❌ না | ❌ না | সাধারণত নতুন রিসোর্স তৈরি করে। ১০ বার কল করলে ১০টি আলাদা অর্ডার তৈরি হতে পারে। |
| **PATCH** | ❌ সাধারণ অর্থে না | ❌ না | আংশিক আপডেট। যদি ইনক্রিমেন্ট অপারেশন হয় (`{"balance": balance + 10}`) তবে এটি নন-আইডেমপোটেন্ট। |

### 3. Production Architecture: Distributed Idempotency Key Flow

```
[ Client / Mobile App ]
       │
       │ (1) POST /api/v1/orders
       │     Header -> Idempotency-Key: 7b2c9a1d-4e8f-4a3b
       ▼
[ API Gateway / Microservice ]
       │
       │ (2) Atomic SETNX in Redis
       │     SET "idemp:7b2c9a1d-4e8f-4a3b" '{"status":"PROCESSING"}' NX EX 120
       ▼
   ┌───────────────────────────────────────────────────────────┐
   │ Was Key successfully acquired (Key was absent)?           │
   └───────────────┬───────────────────────────┬───────────────┘
                   │ [ YES ]                   │ [ NO: Key Exists ]
                   ▼                           ▼
      ┌─────────────────────────┐  ┌─────────────────────────────────────┐
      │ Process Payment & Order │  │ Check existing Redis status:        │
      │ Transaction in DB       │  │ - "PROCESSING": Return 409 Conflict │
      └────────────┬────────────┘  │ - "COMPLETED":  Return Cached Body  │
                   │               └─────────────────────────────────────┘
                   ▼
      ┌─────────────────────────┐
      │ Update Redis Value:     │
      │ '{"status":"COMPLETED", │
      │   "response": {...}}'   │
      │ EX 86400 (24 hours)     │
      └────────────┬────────────┘
                   │
                   ▼
      Return 201 Created to Client
```

### 4. স্টেপ-বাই-স্টেপ মেকানিজম ও রেস কন্ডিশন হ্যান্ডলিং

1. **Client Generation:** ক্লায়েন্ট একটি ইউনিক আইডেমপোটেন্সি কি তৈরি করে (সাধারণত UUID v4)।
2. **Distributed Atomic Locking:**
   - ডিস্ট্রিবিউটেড ক্যাশে (Redis) এ একটি অ্যাটমিক কম্যান্ড চালানো হয়:
     ```redis
     SET idempotency_key:UUID '{"status":"STARTED"}' NX EX 120
     ```
   - `NX` (Not Exists) নিশ্চিত করে শুধুমাত্র প্রথম রিকোয়েস্টই লক পাবে।
3. **In-Flight Concurrent Request:** যদি একই কি সহ দ্বিতীয় আরেকটি রিকোয়েস্ট প্রথমটি প্রসেস হওয়ার মাঝপথেই চলে আসে:
   - Redis দেখে স্ট্যাটাস এখনো `STARTED`/`PROCESSING`।
   - সার্ভার অবিলম্বে `409 Conflict` বা `425 Too Early` অথবা `Retry-After: 2` হেডারসহ রিটার্ন করে।
4. **Completion & Result Caching:**
   - ডেটাবেজ ট্রানজ্যাকশন সফল হলে Redis-এ স্ট্যাটাস `COMPLETED` করে রেসপন্স পে-লোডটি ক্যাশ করে রাখা হয় (সাধারণত ২৪ থেকে ৭২ ঘণ্টার জন্য)।
5. **Safe Retry:** পরবর্তীতে নেটওয়ার্ক টাইমআউটের কারণে ক্লায়েন্ট একই কি দিয়ে পুনরায় কল করলে, সার্ভার কোনো বিজনেস কোড এক্সিকিউট না করে সরাসরি ক্যাশড রেসপন্সটি ফিরিয়ে দেয়।

### 5. Failure Modes, Edge Cases & Mitigations

#### Failure Mode 1: Request Fingerprint Mismatch (Payload Tampering)
- **ঝুঁকি:** একজন হ্যাকার বা বাগযুক্ত ক্লায়েন্ট পুরোনো ব্যবহৃত `Idempotency-Key` ব্যবহার করে ভিন্ন কোনো ইউজারের পেমেন্ট বা ভিন্ন অংকের টাকার রিকোয়েস্ট পাঠাল।
- **প্রতিরোধ (Mitigation):** রিকোয়েস্ট বডি এবং পাথ প্যারামিটারের একটি ক্রিপ্টোগ্রাফিক হ্যাশ (SHA-256) তৈরি করে কি-এর সাথে স্টোর করা। পরবর্তীতে কি ম্যাচ করলেও যদি পে-লোড হ্যাশ না মেলে, তবে তৎক্ষণাৎ `422 Unprocessable Entity` ("Idempotency key reused with different payload") রিটার্ন করা।

#### Failure Mode 2: Server Crash Mid-Transaction (Zombie Lock)
- **ঝুঁকি:** সার্ভার Redis-এ `STARTED` মার্ক করল, কিন্তু ডাটাবেজ কমিটের আগে সার্ভার ওওএম (OOM) বা বিদ্যুৎ বিভ্রাটে ক্র্যাশ করল। ফলে কি-টি অনন্তকাল আটকে থাকবে।
- **প্রতিরোধ:** Redis লকে অবশ্যই যুক্তিসঙ্গত এক্সপায়ারি টাইম (`EX 60` বা `120` সেকেন্ডের TTL) থাকতে হবে।

### 6. Senior / Staff Engineer Interview Defense

> **ইন্টারভিউয়ার:** *"পেমেন্ট সিস্টেমে যদি ক্লায়েন্ট একটি পেমেন্ট রিকোয়েস্ট পাঠানোর পর নেটওয়ার্ক টাইমআউট পায়, তবে সে কি রিট্রাই করবে? রিট্রাই করলে ডাবল চার্জিং কীভাবে আটকাবেন?"*
>
> 💡 **Staff-Level উত্তরের কাঠামো:**
> "নেটওয়ার্ক টাইমআউট পাওয়ার অর্থ ক্লায়েন্ট জানে না সার্ভারে রিকোয়েস্টটি পৌঁছেছিল কিনা। ক্লায়েন্ট অবশ্যই রিট্রাই করবে, তবে এটি নিরাপদ করতে আমাদের আর্কিটেকচারে নিচের ৩টি প্রতিরক্ষা স্তর থাকবে:
> 1. **Client Idempotency Key:** ক্লায়েন্ট রিকোয়েস্ট পাঠাতে একটি ক্লায়েন্ট-জেনারেটেড UUIDv4 হেডার বাঁধবে। রিট্রাই করার সময় সে কখনোই নতুন কি তৈরি করবে না, বরং মূল কি-টিই পুনরায় পাঠাবে।
> 2. **Redis Distributed Lock with Payload Fingerprint:** এপিআই গেটওয়েতে `SETNX` দিয়ে লকিং হবে। রিকোয়েস্ট বডির SHA-256 হ্যাশ ভ্যালিডেট হবে। রিকোয়েস্ট সফল হলে রেসপন্স ক্যাশ থাকবে। ডুপ্লিকেট রিট্রাই সরাসরি ক্যাশড রেসপন্স পাবে।
> 3. **Database Unique Constraint (Defense in Depth):** ক্যাশ কোনো কারণে ইভিক্ট হলেও ডাটাবেজে `payment_transactions` টেবিলে `idempotency_key` কলামে একটি `UNIQUE` কনস্ট্রেইন্ট থাকবে। ফলে একই ট্রানজ্যাকশন ডাটাবেজ লেভেলে দ্বিতীয়বার ইনসার্ট হতে গেলে ডেটাবেজ ইউনিক ভায়োলেশন এরর দিয়ে ডাবল-চার্জ শতভাগ প্রতিহত করবে।"

10. Idempotency Key-এর জন্য Redis ক্যাশের মেয়াদ (TTL) কত হওয়া উচিত এবং কেন?

### Advanced / Staff-Level Questions

1. **সংজ্ঞা:** $f(f(x)) = f(x)$। একই অপারেশন একাধিকবার চালালেও সিস্টেমের স্টেট প্রথমবারের মতোই অপরিবর্তিত থাকা।
2. **HTTP মেথডস:** GET, PUT, DELETE হলো স্বাভাবিকভাবে আইডেমপোটেন্ট। POST এবং PATCH নন-আইডেমপোটেন্ট।
3. **Client-generated Key:** ক্লায়েন্ট যদি নেটওয়ার্ক টাইমআউট পায়, সে সার্ভারের কোনো রেসপন্স পায়নি। তাই ক্লায়েন্টই একমাত্র সত্ত্বা যে জানে পরবর্তী রিট্রাইটি পূর্ববর্তী রিকোয়েস্টেরই পুনরাবৃত্তি।
4. **409 Conflict:** যখন একই কি সহ প্রথম রিকোয়েস্টটি এখনো সার্ভারে প্রসেসিং অবস্থায় (In-flight) থাকে এবং ঠিক সেই মুহূর্তে কনকারেন্ট আরেকটি ডুপ্লিকেট রিকোয়েস্ট এসে পৌঁছায়।
5. **DELETE Idempotent কেন:** আইডেমপোটেন্সির সংজ্ঞা হলো সিস্টেম স্টেটের ওপর প্রভাব, স্ট্যাটাস কোড নয়। প্রথম কলে রিসোর্স মুছে যায়, দ্বিতীয় কলেও রিসোর্সটি মুছে যাওয়ার স্টেতেই থাকে (রিসোর্স অনুপস্থিত)।
6. **Redis NX EX:** `NX` নিশ্চিত করে কি-টি না থাকলেই কেবল বসবে (Atomic Lock); `EX` নিশ্চিত করে সার্ভার ক্র্যাশ করলেও নির্দিষ্ট সময় পর লকটি অটো রিলিজ হবে।
7. **Request Fingerprint:** রিকোয়েস্ট পে-লোড ও ইউআরএল-এর SHA-256 হ্যাশ। একই কি দিয়ে কেউ যদি ভিন্ন ডেটা সাবমিট করে প্রতারণা করতে চায়, তবে সিস্টেম তা ধরে ফেলে `422 Unprocessable Entity` দেয়।
8. **DB Commit succeeded but Cache failed:** রিট্রাই আসলে Redis-এ কিছু না পেয়ে ডাটাবেজে যাবে। ডাটাবেজে `UNIQUE` কনস্ট্রেইন্ট ভায়োলেশন ধরে সিস্টেম বুঝতে পারবে অপারেশনটি ইতিমধ্যে সফল হয়েছে এবং ডাটাবেজ থেকে ডেটা তুলে রেসপন্স ফেরত দেবে।
9. **Idempotent Kafka Consumer:** প্রসেস করার আগে মেসেজের ইউনিক অফসেট বা বিজনেস আইডি একটি ডিবি বা রেডিস টেবিলে ইনসার্ট করা। আগে প্রসেস হয়ে থাকলে স্কিপ করা (Inbox Pattern)।
10. **TTL নির্ধারণ:** সাধারণত ২৪ ঘণ্টা থেকে ৭২ ঘণ্টা। বিজনেস লজিকে ক্লায়েন্টের রিট্রাই সাধারণত কয়েক সেকেন্ড বা মিনিটের মধ্যেই শেষ হয়, তবে কিছু অফলাইন মোবাইল ক্লায়েন্ট ২৪ ঘণ্টার মধ্যে রিট্রাই করতে পারে।
11. **Multi-Region Idempotency:** গ্লোবাল লকিং অতিরিক্ত ল্যাটেন্সি বাড়ায়। তাই অ্যাকাউন্ট আইডি বা ইউজার আইডি হ্যাশ করে নির্দিষ্ট রিজিয়নে ট্রাফিক রাউট করা (Affinity Routing), যাতে একই ইউজারের রিট্রাই একই রিজিয়নের লোকাল রেডিসে হিট করে।
12. **Stripe Idempotency:** স্ট্রাইপ প্রতিটি POST রিকোয়েস্টে `Idempotency-Key` গ্রহণ করে, তাদের অ্যাকটিভ-অ্যাকটিভ লেয়ারে রিকোয়েস্ট পে-লোড ও স্টেট ক্যাশ করে এবং ফেইলিউরে সেভড রেসপন্স রিপ্লে করে।
13. **Outbox + Idempotent Consumer:** প্রডিউসার ডাটাবেজ ট্রানজ্যাকশনের সাথে আউmessages টেবিলে ইভেন্ট লিখে; কনজিউমার মেসেজ প্রসেস করার সময় নিজস্ব ইনবক্স টেবিলে মেসেজ আইডি সেভ করে ডুপ্লিকেট ড্রপ করে।
14. **Long-running Jobs:** ক্লায়েন্টকে সাথে সাথে `202 Accepted` এবং একটি `Job-ID` বা স্ট্যাটাস চেকিং ইউআরএল রিটার্ন করা। পরবর্তীতে ক্লায়েন্ট একই কি দিলে নতুন কাজ শুরু না করে প্রগ্রেস স্ট্যাটাস দেওয়া।
15. **Banking State Machine:** ইন-প্লেস যোগ/বিয়োগের বদলে ট্রানজ্যাকশনকে একটি ইউনিক `Transaction-ID` সমৃদ্ধ ইমিউটেবল লেজার এন্ট্রিতে রূপান্তর করা। লেজারে `UNIQUE(account_id, reference_id)` রাখা, ফলে একই রেফারেন্স আইডিতে একাধিকবার ডেবিট হওয়া অসম্ভব।
